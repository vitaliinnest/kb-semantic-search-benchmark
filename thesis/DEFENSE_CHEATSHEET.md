# Defense Cheatsheet — компактна шпаргалка для Fast Mode

> **Призначення:** одна сторінка з усім, що потрібно для швидкої відповіді під час захисту. Defense-mode читає це **першим**, перед SLIDES_REF.md. Усе компактно: keyword → 2-3 речення.
>
> **Структура:** ключові цифри → терміни → чому-питання → готові короткі відповіді.

---

## Ключові цифри (для звірки)

### Корпус
- **32 документи** (10 tech + 13 legal + 9 medical)
- **300 запитів** (по 100 на домен)
- **200 qrels** (релевантні пари «запит-чанк»)
- **Чанк** ~600 слів з перекриттям

### Моделі (параметри / max токенів / архітектура)
- **BGE-M3:** 568M / 8192 / Encoder dense+sparse+multi-vector
- **E5-base:** 278M / 512 / Encoder (multilingual)
- **nomic-embed v1.5:** 137M / 8192 / Encoder + Matryoshka
- **Qwen3-Embedding-0.6B:** 596M / 32768 / Decoder (LLM-based)
- **BM25 (Okapi):** опорна модель, без нейромережі

### Результати nDCG@10
- **Tech:** BGE 0.6722 > Qwen3 0.6325 > E5 0.6121 > BM25 0.4861 > nomic 0.3765
- **Legal:** Qwen3 0.3199 > BGE 0.3065 > E5 0.2567 > BM25 0.1875 > nomic 0.0951
- **Medical:** BGE 0.4339 > E5 0.3909 > Qwen3 0.3629 > BM25 0.3222 > nomic 0.1668

### Латентність (мс/запит)
- BM25 <3 / E5 ~70 / nomic ~125 / BGE ~228 / Qwen3 ~440

### Bootstrap 95% CI (tech, nDCG@10)
- BGE-M3: **[0.606 ; 0.737]**
- BM25:   **[0.431 ; 0.541]**
- Інтервали не перетинаються — статистично значуща різниця

### Парето-множина (tech)
- {BGE-M3, E5-base, BM25}

## Терміни (одне речення кожен)

- **nDCG@10** — нормалізована якість ранжування у топ-10, врахування і релевантності, і позиції; 0-1, вище краще.
- **MRR@10** — середня обернена позиція першого релевантного документа; 0-1, вище краще.
- **Recall@10** — частка знайдених релевантних серед усіх релевантних; 0-1, вище краще.
- **Precision@10** — частка релевантних серед перших 10 результатів; 0-1, вище краще.
- **bootstrap CI** — 2000 повторних випадкових вибірок з поверненням, далі 2.5-й і 97.5-й перцентилі дають 95% довірчий інтервал.
- **Парето-домінування** — модель A домінує модель B, якщо A не гірша за усіма критеріями і краща хоча б за одним.
- **Парето-множина (фронт)** — моделі, які не домінуються жодною іншою; раціональні варіанти.
- **MCDA / МКВ** — багатокритеріальний вибір; у роботі = Парето + лінійна адитивна згортка з ваговими коефіцієнтами.
- **Лінійна адитивна згортка** — інтегральна оцінка U(a) = Σ wⱼ · yⱼ; ваги задаються користувачем.
- **qrels** — query relevance, експертна розмітка з градаціями релевантності (0, 1, 2).
- **Чанк** — фрагмент документа ~600 слів, одиниця ранжування.
- **FAISS** — бібліотека для швидкого пошуку найближчих векторів; використано IndexFlatIP (точний пошук).
- **L2-нормалізація** — приведення вектора до одиничної довжини; після цього inner product = косинусна схожість.

## Чому-питання → короткі відповіді

### Чому k=10?
Стандарт у IR (TREC, BEIR, MTEB). Відповідає реальній поведінці користувача — 85-90% не йдуть далі першої сторінки видачі. Балансує між Recall (потрібен великий k) і Precision (потрібен малий k); k=10 — точка найкращої диференціації моделей.

### Чому 32 документи / 300 запитів?
Достатньо для статистичної значущості — підтверджено бутстрепом, CI не перетинаються. Реалістично для ручної експертної розмітки qrels; більший набір вимагав би команди розмітників.

### Чому 600 слів у чанку?
Компроміс між самодостатністю фрагмента (одна концепція — один чанк) і обмеженням контексту моделей. Помічається в max_tokens усіх 4 моделей (512 у E5 — найменший, ~780 токенів = 600 слів × 1.3).

### Чому ці три домени?
Максимально різні лінгвістично: tech (англіцизми, концепти), legal (формальна мова, складна семантика), medical (термінологія, латинські назви). Якщо модель робастна на трьох — це не випадковість одного домену.

### Чому ці 4 моделі?
Сучасні embedding-моделі різних архітектур: BGE-M3 (multi-functional encoder, мультимовний лідер), E5-base (швидкий encoder з префіксами), nomic (компактна з Matryoshka), Qwen3 (єдина decoder-based на LLM). Покривають весь спектр архітектур станом на 2025.

### Чому BM25 — опорна модель?
Стандарт IR-літератури; точка відліку «чи варто переходити з лексичного пошуку на embedding?»; Парето-екстремум за швидкодією (<3 мс). Робота не про порівняння з BM25 — вона про обґрунтований вибір embedding-моделі.

### Чому Парето + лінійна згортка, а не TOPSIS / AHP / ELECTRE?
Лінійна згортка — проста, інтерпретована, користувач прямо контролює ваги. Парето першим відсіює явно гірші моделі — менше альтернатив для зважування. Альтернативні методи додали б складності без переваги для нашої задачі.

### Чому FAISS IndexFlatIP, а не HNSW / IVF?
IndexFlatIP — точний пошук без апроксимації. Для 32 документів (~кілька сотень чанків) точна швидкість висока. HNSW / IVF потрібні для мільйонів векторів, тут зайва складність без вигоди.

### Чому L2-нормалізація + inner product, а не cosine напряму?
Математично еквівалентно: cos(a, b) = a·b якщо ||a||=||b||=1. Inner product на L2-нормалізованих векторах швидший за обчислення cosine (немає ділення на норми кожного разу).

### Чому 2000 ітерацій бутстрепу?
Стандарт з Efron & Tibshirani 1993. Менше — границі CI плавають при повторних запусках, більше — лише гайнує час без додаткової точності.

### Чому 95% CI?
Стандарт у науці. 99% — інтервали ширші, складніше відрізнити моделі; 90% — вужчі, але слабкіші висновки.

### Чому система працює локально на CPU?
Embedding-моделі не великі мовні моделі: 137-596M параметрів (LLM 7B+), один прохід обчислення на запит, документи кодуються одноразово при побудові індексу. Більшість моделей — encoder-only (BERT-стиль), структурно дешевші за decoder-based LLM.

### Чому nomic — найгірша?
Слабке покриття української в тренувальних даних. Контрастивне навчання було сфокусоване на англомовних парах. Розмір моделі — лише один фактор; критичні саме мова і метод тренування.

### Чому Qwen3 (596M) гірша за BGE-M3 (568M)?
Decoder-LLM архітектура повільніша за encoder (~2× повільніша). Тренувальні дані Qwen3 не оптимізовані спеціально для retrieval. Розмір ≠ якість.

### Які гіпотези підтверджено?
**H1:** embedding-моделі статистично значуще переважають BM25 на українській — підтверджено (CI не перетинаються).
**H2:** немає універсального лідера; оптимальна модель залежить від домену і пріоритетів — підтверджено (Qwen3 лідер на legal, BGE на tech/medical; Парето-множина = 3 моделі).

### Яка новизна (від керівника)?
Комплексне benchmark-дослідження сучасних embedding-моделей для семантичного пошуку в корпоративних базах знань із використанням багатокритеріального оцінювання та засобів інтерпретації retrieval-результатів.

### Практична значущість?
Готовий до впровадження Flask-застосунок з вбудованим багатокритеріальним вибором моделі. Підтримує PDF/DOCX/TXT/MD. Українські організації можуть одразу використовувати для семантичного пошуку у власних базах. Усі моделі open-source, локально, без передачі даних у хмару.

## Висновок (одне речення)

**Обґрунтовано рекомендації щодо вибору embedding-моделі для україномовного семантичного пошуку у корпоративних базах знань методом багатокритеріального аналізу.**

## Рекомендації по моделях

- **BGE-M3** — основна модель, найкраща якість і стабільність у різних доменах.
- **E5-base** — швидка альтернатива, якість на ~10% нижча за BGE, але утричі швидше.
- **Qwen3** — для юридичних колекцій (єдина, де лідер за nDCG).
- **BM25** — гранично жорсткі вимоги до швидкості (<3 мс) або як опорний метод.
- **nomic** — не рекомендується для українських корпусів.

## Перспективи розвитку (якщо спитають «що далі»)

- **Fine-tuning** обраної моделі на доменно-специфічних даних
- **Hybrid retrieval** — комбінація BGE-M3 + BM25 з RRF (Reciprocal Rank Fusion)
- **Re-ranking** — додати cross-encoder для перерангування топ-100 у топ-10
- **RAG-інтеграція** — додати LLM для генерації відповідей на основі знайдених чанків
- **Розширення benchmark** — більше доменів, більше запитів, краща розмітка
