## 1. Інтуїція

### Як «закодувати сенс»

Уяви, що ти описуєш кота через числа:
- «розмір»: 0.2 (на шкалі 0=миша, 1=слон)
- «пушистість»: 0.9
- «незалежність характеру»: 0.8
- «здатність плавати»: 0.1

Тепер кіт — це вектор `[0.2, 0.9, 0.8, 0.1]`.

Кішка — приблизно те саме: `[0.18, 0.92, 0.85, 0.1]`. Вектори **близькі**.
Собака: `[0.3, 0.6, 0.3, 0.6]` — пушистий, але плаває, менш незалежний. Інший вектор.
Велосипед: `[0.4, 0.0, 0.0, 0.0]`. Зовсім інший.

Якщо взяти **достатньо вимірів** (768 чи 1024), можна закодувати **сенс** будь-якого тексту так, що схожі за змістом тексти матимуть близькі координати.

**Важливо:** в реальних embedding-моделях **виміри не мають назв**. Ми не можемо сказати: «3-й вимір — це пушистість». Модель сама «вирішує», що кодувати в кожному вимірі під час тренування. Це **прихований простір (latent space)**.

### Чому це працює

Бо модель тренувалась на **мільйонах прикладів** того, що є схожим, а що — різним. Поступово вона навчилася проєктувати тексти так, щоб задовольняти ці обмеження.

## 2. Класичний приклад: word arithmetic

У 2013 році Tomas Mikolov показав фокус. Натренували Word2Vec. Подивилися, що відбувається:

```
вектор("king") − вектор("man") + вектор("woman") ≈ вектор("queen")
```

Це означає, що модель **закодувала концепцію статі** як певний **напрямок** у просторі векторів. Віднявши «man» і додавши «woman», ти зрушив у векторі цей самий напрямок.

Інші приклади з Word2Vec:
```
Paris − France + Italy ≈ Rome     (столиця → столиця)
walking − walk + swim ≈ swimming   (теперішній → ing-форма)
better − good + bad ≈ worse        (порівняльна форма)
```

**Це** доводить, що embeddings — не випадковий набір чисел. Вони **систематично відображають семантичні відношення**.

### Чому це важливо для твоєї роботи

Бо твоя задача — пошук, а пошук = «знайти семантично близькі тексти». Якщо модель кодує сенс — пошук просто полягає у пошуку найближчих векторів. Це **геометрія сенсу**.

## 3. Від слів до речень: контекстуальні vs статичні embeddings

### Word2Vec, GloVe, FastText — статичні

Слово має **один** вектор, незалежно від контексту. Наприклад:
- «банк» (фінансова установа) і «банк» (берег річки) — **той самий вектор**.
- Це обмеження. Реальні тексти неоднозначні.

### BERT, Sentence-BERT, E5, BGE-M3 — контекстуальні

Слово отримує **різний** вектор залежно від контексту:
- «Поклав гроші в **банк**» → один вектор для «банк»
- «Сидимо на **банку** річки» → інший вектор для «банку»

Як це досягається? Через **attention mechanism** трансформера — слово «бачить» сусідні слова під час обчислення свого вектора.

### Sentence-level embeddings

Для пошуку нам треба вектор **цілого фрагменту** (чанка), не окремих слів. Тому моделі додають **pooling**:
- Беруть вектори всіх слів у реченні
- Зливають їх в один вектор (через усереднення, або через [CLS] токен)

Результат — **один вектор на цілий чанк**, який кодує його загальний зміст.

## 4. Як працює сучасний трансформер-енкодер

Це детальний flow, корисно для глибокого розуміння. Не страшно, якщо тут заплутаєшся — основні концепції (1, 2, 3) важливіші.

### Крок 1: Токенізація

Текст розбивається на **токени** (зазвичай subword pieces). Українське «семантичний» може стати `[семант, ##ичний]` — два токени.

```
"Дослідження embeddings" → 
["До", "##слід", "##ження", "embedd", "##ings"]
```

Кожен токен отримує **ID** у словнику моделі (зазвичай 30K-250K записів).

### Крок 2: Token embeddings

Кожен токен ID → **вектор фіксованої розмірності** (наприклад 768).

Це — стартова точка. Вектор статичний (один на ID), без контексту.

### Крок 3: Position encoding

Додається інформація про **позицію** токена у реченні. Бо трансформер сам по собі не знає, де слово в реченні (на відміну від RNN).

### Крок 4: Self-attention (багато шарів)

Це **серце трансформера**. Кожен токен «дивиться» на інші токени і оновлює свій вектор:

```
Для токена «банк»:
  «банк» дивиться на «гроші», «поклав», «у» → 
  розуміє, що це фінансова установа → 
  оновлює свій вектор у цьому напрямку
```

Це повторюється у **12-24 шари** (Layer 1 → Layer 2 → ... → Layer N).

### Крок 5: Output — матриця токен-векторів

Після всіх шарів на виході — **матриця** розміру `[N токенів × розмірність]`. Наприклад, для речення з 50 токенів і моделі з dim=768: матриця 50×768.

### Крок 6: Pooling → один вектор

Матриця стискається в **один вектор** розмірності 768 (наступний розділ).

## 5. Pooling: як з матриці виходить один вектор

Це техніка перетворення матриці [N × D] у вектор [D].

### Метод 1: Mean pooling

Найпростіший: **усереднюємо** вектори всіх токенів.

```python
sentence_vector = token_vectors.mean(axis=0)
```

Це робить **Sentence-BERT, E5, BGE-M3**.

### Метод 2: [CLS] token

Беремо вектор спеціального токена `[CLS]`, який додано на початок речення. Модель навчена концентрувати «сенс речення» у цьому токені.

```python
sentence_vector = token_vectors[0]   # [CLS] завжди першим
```

Це робить **класичний BERT** (без додаткового тренування).

### Метод 3: Max pooling

По кожному виміру беремо **максимум** серед усіх токенів.

```python
sentence_vector = token_vectors.max(axis=0)
```

Рідше використовується.

### Метод 4: Last token (decoder моделі)

Для **decoder-моделей** (як Qwen3-Embedding) беруть вектор **останнього** токена, бо decoder обробляє текст зліва направо і останній токен «бачив» все попереднє.

```python
sentence_vector = token_vectors[-1]
```

**Це** дуже важливо для розуміння Qwen3. Архітектурна особливість.

### Який метод найкращий

Залежить від моделі і задачі. У сучасних embedding-моделях найчастіше — **mean pooling** (E5, BGE-M3). Sentence-BERT дозволяє вибирати. Qwen3 — last token.

**Тобі знати:** modes pooling — це **технічна деталь моделі**. Ти не вибираєш — вибрав автор моделі. Твоя задача — використати модель за документацією.

## 6. Contrastive learning

Це найважливіша частина для розуміння: **як модель «вчиться сенсу»**.

### Ідея

Дано величезний датасет **пар текстів**. Деякі пари — **подібні** за сенсом (positives), деякі — **різні** (negatives). Модель тренується так, щоб:

- Для positive пар → їхні вектори **зближувались**
- Для negative пар → їхні вектори **віддалялись**

### Triplet loss

Класичний метод: дано анкор, позитив, негатив:

```
Анкор:     "що таке нейромережа"
Позитив:   "нейронні мережі — це обчислювальні моделі..."
Негатив:   "рецепт борщу з курятини"
```

Loss функція:
```
loss = max(0, distance(anchor, positive) − distance(anchor, negative) + margin)
```

Модель **штрафується**, якщо відстань до позитиву **більша** за відстань до негативу (з певним зазором/margin).

### InfoNCE / In-batch negatives

Сучасні моделі (E5, BGE-M3) використовують **batch negatives**: в одному батчі — багато пар (q1,d1), (q2,d2)... Для кожного запиту q_i — позитив d_i, а **всі інші** d_j у батчі — негативи.

Це дає тисячі негативів безкоштовно (без додаткових даних).

### Hard negatives

«Складні» негативи — це тексти, які **виглядають** схожими, але не є релевантними. Наприклад:

```
Анкор: "Як працюють бета-блокатори"
Позитив: "Бета-адреноблокатори знижують частоту серцевих скорочень..."
Hard negative: "Альфа-блокатори впливають на тонус судин..."  ← виглядає схоже!
Easy negative: "Як приготувати пасту карбонара"
```

Hard negatives — корисніші для тренування, але їх треба спеціально майнити.

### Чому це працює

Уяви, що ти змушуєш мережу робити **геометрію**, де семантично схожі речі **близько**. Поступово вона вивчає, що:
- «Кіт» і «кішка» — рідко є в одних і тих самих парах як negatives → вектори зближаються
- «Кіт» і «банк» — часто з'являються як negatives → вектори віддаляються
- І так — мільйони комбінацій

Геометрія простору **поступово відображає семантику**.

## 7. Чому 768 або 1024

«Чому ця розмірність, а не 100 чи 5000?» — запитання, яке може спитати комісія.

### Trade-off

| Розмірність | Плюси | Мінуси |
|---|---|---|
| Маленька (32-128) | Швидко, мало пам'яті | Втрачає нюанси сенсу |
| Середня (256-512) | Баланс | — |
| Велика (768-1024) | Багато інформації, висока якість | Повільніше, більше пам'яті |
| Дуже велика (4096+) | Іноді ще краще | Гранична віддача, дуже дорого |

**Стандарт у літературі:** 768 (BERT-base) і 1024 (BERT-large). Це історичні дефолти, від яких відштовхуються нові моделі.

### Як обирається

Зазвичай — як **функція розміру моделі**:
- BERT-base: 12 шарів × 768 dim = 110M параметрів
- BERT-large: 24 шари × 1024 dim = 340M параметрів
- BGE-M3 (568M parameters) → 1024 dim
- E5-base (278M) → 768 dim
- nomic (137M) → 768 dim

### Matryoshka — спеціальне рішення

Nomic (і деякі сучасні моделі) використовує **Matryoshka Representation Learning**: модель тренована так, що перші **k вимірів** вектора вже містять достатньо інформації. Можна обрізати:

```
повний вектор:    [v_1, v_2, ..., v_768]      ← найкраща якість
обрізаний 256:    [v_1, v_2, ..., v_256]      ← гірше, але прийнятно
обрізаний 64:     [v_1, v_2, ..., v_64]       ← компактно
```

Це **технічна особливість**. У твоїй роботі — не використовується (просто факт).

## 8. Encoder vs Decoder моделі

Важлива архітектурна відмінність.

### Encoder (BERT, E5, BGE-M3, nomic)

- Бачить **усі** токени одночасно
- Bidirectional self-attention (можна дивитися вліво і вправо)
- Pooling після всіх шарів → один вектор
- **Сильна сторона:** контекстуальне розуміння в обидві сторони
- Зазвичай **менші** моделі (100-600 M параметрів)

### Decoder (Qwen3-Embedding, GPT-стиль)

- Бачить токени **зліва направо** (causal masking)
- Autoregressive — спочатку для генерації тексту
- Адаптовані для embedding: останній токен як sentence vector
- **Сильна сторона:** можуть слідувати інструкціям («Знайди документ про...»)
- Зазвичай **більші** моделі (LLM-scale: від 500M до десятків мільярдів)

### Чому це важливо

- Encoder моделі — **класика** для retrieval. Швидкі, ефективні.
- Decoder моделі — **нова парадигма**. Через те, що це адаптовані LLM, вони **краще розуміють контекст** і **підтримують інструкції**.
- Qwen3-Embedding-0.6B у твоїй роботі — приклад decoder-моделі. Тому на legal-домені вона лідирує (юр-тексти потребують глибшого розуміння контексту).

### Майбутнє

Тенденція 2024-2025: **decoder-based embedding моделі переростають encoder-based** на MTEB-бенчмарках. Qwen3-Embedding — одна з перших таких.

## 9. Що може піти не так

Поширені помилки, корисно знати для Q&A.

### ❌ Неправильні префікси

E5 моделі **вимагають**:
```
запит:       "query: твій запит"
документ:    "passage: текст документа"
```

Якщо забути — модель **працює**, але дає **гірші** embeddings. Якість падає на 5-15%. У твоєму коді (`src/embedding_models.py:E5EmbeddingModel`) це коректно реалізовано.

### ❌ Різні моделі для індексу і запиту

Документи закодовані BGE-M3, а запит — E5? Космос різний → cosine similarity безглузда → пошук поверне сміття. У твоєму коді `do_search()` бере модель з тих самих artifacts, що індекс — тому гарантовано однакова.

### ❌ Забути нормалізацію

Якщо вектори не L2-нормалізовані, але індекс — FlatIP, то ти отримуєш dot product, а не cosine. Результати все одно якісь, але **не математично коректна косинусна схожість** — пошук буде упереджений у бік довших векторів.

### ❌ Превищити max context

E5-base має max 512 токенів. Якщо чанк більший — модель **обріже** (truncation), втратиш частину сенсу. Тому у твоєму коді `max_seq_length=256` для E5 — обережно.

### ❌ Mixed-language confusion

Старі моделі (тільки англійська) на українському тексті дадуть **майже випадкові** вектори. Це і робить nomic слабкою на укр-даних (тренована переважно англійською).

### ❌ Out-of-domain

Модель, тренована на новинах, на юридичних текстах може давати погану якість. Це часта проблема у спеціалізованих доменах. У твоїй роботі — побічно видно з результатів: legal-домен складніший для всіх.

## 11. Перевірочні питання з відповідями

### Q1. Що таке розмірність вектора ембеддінгу? Чому різні моделі мають різну розмірність?

**A:** Розмірність — кількість координат вектора. У BGE-M3 і Qwen3 — **1024**, у E5-base і nomic — **768**. Це **архітектурний вибір** автора моделі: більше параметрів → зазвичай більша dim. Дим — не єдиний фактор якості; модель з dim=768 може бути кращою за модель з dim=1024, бо якість залежить ще від тренувальних даних, архітектури, кількості шарів.

### Q2. Поясни ідею контрастивного навчання.

**A:** Модель тренується на парах **(анкор, позитив)** і **(анкор, негатив)**. Loss-функція **штрафує** її, якщо вектор позитива далекий від анкора, або якщо негатив близький. Поступово модель навчається проєктувати схожі за змістом тексти у близькі точки простору, а різні — у далекі.

### Q3. Чому TF-IDF не дасть тобі семантичного пошуку?

**A:** TF-IDF працює на рівні слів. «Відтік» і «churn» — різні слова → різні TF-IDF вектори → не близькі. Семантичний пошук вимагає, щоб ця пара була **близькою** — а це досягається лише через нейромережу, навчену на семантично подібних парах.

### Q4. Як з матриці token-vectors виходить один sentence-vector?

**A:** Через **pooling**. Найчастіше — **mean pooling** (усереднення по токенах). Альтернативи: [CLS] token (BERT), max pooling, last-token (Qwen3 — для decoder-моделей).

### Q5. Що означає «контекстуальний embedding» на відміну від статичного?

**A:** **Статичний** (Word2Vec) — кожне слово має один вектор, незалежно від контексту. «Банк» (фінанси) і «банк» (річка) — однаковий вектор. **Контекстуальний** (BERT, E5, BGE-M3) — модель «дивиться» на сусідні слова через self-attention і генерує **різні** вектори для одного і того самого слова в різних контекстах.

### Q6. Поясни роль self-attention у трансформері.

**A:** Self-attention — це механізм, у якому кожен токен «дивиться» на інші токени у реченні і **оновлює свій вектор** на основі контексту. Це робиться у **багатьох шарах** (12 для base, 24 для large). Завдяки цьому модель розуміє складні залежності — наприклад, що «банк» у контексті «гроші», «вклад» — про фінансову установу.

### Q7. Чому E5 вимагає префіксів?

**A:** E5 тренована на парах **(query, passage)**, де кожна сторона мала чіткий префікс «query:» або «passage:». Так модель навчилася відрізняти запит від документа і оптимізувати embedding під свою роль. Якщо не додати префікс — модель «не знає», що це — і дає менш специфічний embedding.

### Q8. Чим Qwen3-Embedding принципово відрізняється від BGE-M3?

**A:** Архітектурно. BGE-M3 — **encoder** (bidirectional, як BERT). Qwen3 — **decoder** (autoregressive, як GPT). Це означає різний механізм self-attention (Qwen3 — causal). На практиці: Qwen3 краще розуміє складний контекст і підтримує інструкції; BGE-M3 — швидша і ефективніша на простіших задачах. У твоїх результатах: Qwen3 — лідер на legal, BGE-M3 — на tech і medical.

### Q9. Що таке Matryoshka representations?

**A:** Метод тренування, при якому **перші k вимірів** вектора містять найважливішу інформацію. Це дозволяє **обрізати** вектор до меншої розмірності (768 → 256 → 64) із поступовою втратою якості. Корисно, коли треба компромісувати розмір індексу. У nomic-embed v1.5 — використовується. У твоїй роботі — не використовується (нормально, не входило в скоп).

### Q10. Якщо я бачу, що nomic дає поганий результат на українській — у чому причина?

**A:** Найімовірніше — **тренувальні дані**. Nomic тренована на переважно англомовних парах, з обмеженим використанням української. Тому її embedding-простір **не оптимально розкладає** український текст. Це не дефект моделі — це **відсутність domain coverage**. Розв'язання: fine-tuning на українських даних або вибір кращої multilingual моделі (BGE-M3).
