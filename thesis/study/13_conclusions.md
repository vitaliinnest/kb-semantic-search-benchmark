# 13. Висновки і практичні рекомендації

> **TL;DR:** Робота довела статистично значущу перевагу embedding-моделей над BM25 на українських корпоративних колекціях. **BGE-M3** — основна рекомендація для впровадження. **E5-base** — швидка альтернатива. **Qwen3** — для legal-домену. **BM25** — як baseline і для real-time. **Nomic** — не рекомендується. Подальші роботи: fine-tuning, hybrid retrieval, ширший benchmark.

## 1. Підтверджені гіпотези

### Гіпотеза 1: Embeddings > BM25 (для правильно обраних моделей)

**Підтверджена.** На технічному домені BGE-M3 (0.6722) значно переважає BM25 (0.4861). 95% CI не перетинаються — **статистично значуща** перевага.

Це **головна заявлена гіпотеза** роботи. Підтверджена.

### Гіпотеза 2: Не всі embeddings однакові

**Підтверджена.** Розкид між BGE-M3 (0.4708 середній nDCG) і nomic (0.2128) — 0.258. Більше, ніж розкид між BM25 і кращими embedding-моделями. Тобто **вибір конкретної моделі** важливіший, ніж вибір «класу методу».

### Гіпотеза 3: Оптимальна модель залежить від домена

**Підтверджена.** На tech — BGE-M3 лідер за nDCG. На legal — Qwen3. На medical — BGE-M3. **Універсального переможця нема**. Це обґрунтовує **необхідність експериментального підходу до вибору** моделі.

### Гіпотеза 4: Multi-criteria selection дає інші рекомендації, ніж single-criterion

**Підтверджена.** На legal: за чистим nDCG лідер Qwen3, за MCDA — BGE-M3 (через швидкодію і інші критерії). Це показує важливість **збалансованого** підходу до вибору.

### Гіпотеза 5: Bootstrap-метод дає робастну статистичну оцінку

**Підтверджена.** Метод стабільний з 2000 ітерацій, CI повторюються при різних запусках. Інтервали узгоджуються з очікуваною теорією (95% покриття).

## 2. Чого робота **не** довела

Чесне визнання обмежень:

### ❌ «Embeddings завжди краще за BM25»

**Спростовано** твоїми ж результатами. nomic — embedding модель — гірше за BM25 на 2 з 3 доменів. «Embedding» не = «краще автоматично».

### ❌ «BGE-M3 — універсально найкраща модель»

**Не доведено.** На legal-домені за nDCG лідер — Qwen3. BGE-M3 — **переважно** найкраща, але **не у всіх метриках і всіх доменах**.

### ❌ «Лінійна згортка — оптимальний MCDA-метод»

**Не доводилось.** Використано лінійну згортку через простоту і інтерпретовність. TOPSIS, AHP можливо дали б трохи різні рекомендації. Це **інженерний вибір**, не наукове твердження про перевагу методу.

### ❌ «Fine-tuning не дав би значного покращення»

**Не перевіряли.** Робота не включала fine-tuning експерименти. Можливо, fine-tuning дав би +5-15% nDCG. Це **відкрите питання**.

### ❌ «Результати масштабуються на мільйони документів»

**Не перевіряли.** На малих корпусах (тисячі чанків). На більших — поведінка може змінитися (особливо латентність і поведінка ANN-індексів).

## 3. Практичні рекомендації за сценаріями

### Загальна корпоративна KB

**Рекомендація: BGE-M3**

- Найкраща якість на більшості доменів
- Робастна — близько до лідера навіть там, де не перше місце
- Multilingual, підтримує українську
- ~220 мс на запит — прийнятно для більшості застосувань

### Real-time chatbot

**Рекомендація: E5-base**

- 70 мс на запит — у 3 рази швидше за BGE-M3
- Якість трохи нижче (10-15%), але прийнятна
- Менша модель → менше пам'яті

### Юридичний домен з пріоритетом якості

**Рекомендація: Qwen3-Embedding**

- Лідер на legal за nDCG (0.3199)
- Decoder-архітектура краще обробляє складну юр-логіку
- Найдовший контекст (32K) — підходить для довгих юр-документів
- **Мінус:** найвища латентність

### Дуже жорсткі вимоги до швидкості (< 5 мс)

**Рекомендація: BM25**

- Менше 1 мс на запит
- Якість значно нижче, але **залишається конкурентним** у деяких сценаріях (точні цитати, технічні терміни)
- Майже нульові вимоги до пам'яті

### Edge / mobile (обмежена пам'ять)

**Рекомендація: E5-base або nomic з Matryoshka**

- Менші моделі (278M і 137M відповідно)
- E5-base — кращу якість
- nomic + Matryoshka — можна обрізати вектор до 64-128 dim для compactness

### Hybrid (для максимальної якості)

**Рекомендація: BGE-M3 + BM25 + RRF**

- Кращих результатів зазвичай дають hybrid системи
- Не реалізовано в роботі, але **наступний логічний крок**

## 4. Архітектурні рекомендації для production

### Розмір корпусу

- **< 10K чанків:** IndexFlatIP (точний пошук, мс латентності)
- **10K-1M:** IndexHNSWFlat з M=32 (recall ~98%)
- **1M-100M:** IndexHNSWFlat або IndexIVFFlat
- **> 100M:** Спеціалізована vector DB (Qdrant, Weaviate)

### Деплой моделі

- **CPU-only:** BGE-M3, E5-base — OK; Qwen3 — повільно
- **GPU available:** Все моделі досить швидкі (< 50 мс)
- **Distributed:** оркеструвати кілька реплік (kubernetes)

### Чанкінг

- 500-800 слів — sweet spot
- Overlap ~10-15% довжини чанка
- Розглянути semantic chunking для production

### Моніторинг

- Latency p50, p95, p99
- nDCG@10 на тестовому subset запитів
- Embedding cache hit rate (для повторюваних запитів)

## 5. Перспективи розвитку

Як **прямі продовження** твоєї роботи:

### 1. Fine-tuning найкращих моделей

- Збір більшого тренувального датасету (10K+ пар query-passage)
- Fine-tune BGE-M3 на укр-доменно-специфічних даних
- Очікуваний gain: +5-15% nDCG

### 2. Hybrid retrieval

- BM25 + BGE-M3 з RRF (Reciprocal Rank Fusion)
- Ймовірний gain: +3-7% nDCG над best single model
- Складність системи зростає

### 3. Розширення benchmark

- Більше доменів (HR, фінанси, технічна підтримка)
- Більше запитів (по 200-500 на домен)
- **Graded relevance** замість бінарної (0/1/2/3)
- Cross-domain тести (запит з одного домена → пошук у всіх)

### 4. Експерименти з chunking

- Semantic chunking
- Hierarchical (multi-resolution) chunking
- Recursive chunking з абзацами/реченнями
- Виміряти вплив розміру чанка на якість

### 5. Інтеграція з RAG

- Поверх retrieval (твоя робота) додати **generation**
- LLM формує відповідь на основі топ-K чанків
- Це повна система Q&A

### 6. Production хардення

- Auth, rate limiting
- Multi-tenant
- Logging, monitoring
- A/B testing моделей

### 7. UI покращення

- Підсвічування релевантних фрагментів у тексті
- Filters by metadata (дата, автор, відділ)
- Сomparison view (топ-K від різних моделей)

## 6. Внесок роботи

### Теоретичний

1. **Систематизація** сучасних embedding-моделей з порівняльним аналізом
2. **Багатокритеріальний фреймворк** оцінки моделей з 5 критеріями
3. **Перший публічний benchmark** українських корпоративних колекцій

### Практичний

1. **Готова система** з відкритим кодом (Flask + FAISS)
2. **Веб-інтерфейс** з повним workflow: upload → chunk → index → search → evaluate → select
3. **Інтерактивний MCDA wizard** для вибору моделі під свій сценарій
4. **Bencmark dataset** — 300 запитів × 32 документи × ручні qrels

### Методологічний

1. **Bootstrap CI** як стандарт перевірки значущості (в укр. літературі — рідкісно)
2. **Парето + лінійна згортка** — двоступінчастий MCDA
3. **Доменно-специфічні профілі ваг** — практичний підхід до різнорідних задач

## 7. Обмеження роботи

Чесне визнання — комісія завжди питає.

### Обсяг даних

- 300 запитів — **обмежений** датасет
- Для глибшої статистики треба 1000+ запитів на домен
- qrels формувалися вручну — суб'єктивні моменти

### Кількість моделей

- 4 embedding + BM25
- Не вистачає: OpenAI (потрібен API), Cohere, інші пропрієтарні
- Не вистачає: Sentence-BERT різних розмірів

### Не реалізовано

- Fine-tuning
- Hybrid retrieval
- HNSW / approximate search
- RAG-інтеграція
- Semantic chunking

### Ресурси

- Розроблено на CPU (без GPU)
- Якісь моделі (Qwen3) тестуються на повільних умовах
- На GPU результати були б іншими (особливо за latency)

### Узагальнюваність

- Тестовано на 3 доменах, на українській мові
- Не відомо, як перенесеться на:
  - Інші мови (англійська, російська)
  - Інші домени (фінанси, освіта)
  - Інші розміри корпусів (мільйони документів)

## 8. Підсумкова промова

### На захисті у фіналі (1.5 хвилини)

> Підсумовуючи: у роботі обґрунтовано доцільність застосування сучасних моделей векторних ембеддінгів для семантичного пошуку у корпоративних базах знань. Сформульовано практичні рекомендації щодо вибору моделі.
>
> **BGE-M3** — основна модель для впровадження: найкраща якість і стабільність у різних доменах. Це підтверджено експериментально на 3 доменах.
>
> **E5-base** — швидка альтернатива з прийнятною якістю та триразовою перевагою за швидкодією. Парето-оптимальна.
>
> **Qwen3** — оптимальний вибір для юридичних колекцій, де він демонструє найвищу якість завдяки decoder-архітектурі.
>
> **BM25** — залишається конкурентним baseline у певних доменах і за дуже жорстких вимог до швидкості.
>
> **Nomic** — не рекомендується для українських корпусів через слабке покриття мови у тренувальних даних.
>
> Усі задачі, поставлені в роботі, виконано. Мета досягнута. Розроблено повноцінний веб-застосунок з інтерактивним багатокритеріальним вибором моделі. Опубліковано 2 наукові праці на міжнародних конференціях.
>
> Дякую за увагу! Готовий відповісти на запитання.

## 9. Перевірочні питання з відповідями

### Q1. Які саме гіпотези у роботі ти підтвердив?

**A:**
1. Embedding-моделі статистично значуще переважають BM25 на укр-корпусах (для правильно обраних моделей)
2. Конкретний вибір моделі важливіший, ніж «embedding vs lexical»
3. Оптимальна модель залежить від домена
4. MCDA дає рекомендації, відмінні від single-metric лідерства

### Q2. Чого ти **не** довів?

**A:** Чесно:
- «Embeddings завжди кращі» — спростовано (nomic)
- «BGE-M3 — універсально найкраща» — не доведено
- Не вивчено fine-tuning, hybrid, semantic chunking, RAG
- Не перевіряли на великих корпусах

### Q3. Як ти би відповів на «а може це просто collinearity з розміром моделі»?

**A:** Хороше питання. Більшість моделей — 137M (nomic), 278M (E5), 568M (BGE-M3), 596M (Qwen3). Маленька nomic — найгірша, велика BGE — найкраща. Здається, чим більша — тим краще.

Але:
- Qwen3 (596M) — гірше за BGE-M3 (568M) на tech
- E5 (278M) — на 2-му місці за швидкодією

Розмір **корелює**, але **не визначає** якість повністю. Більше залежить від тренувальних даних і архітектури.

### Q4. Чому це важлива робота для практики?

**A:**
1. **Перший** публічний benchmark для укр-корпорат. KB
2. **Готова система** з відкритим кодом
3. **Інструмент** для обґрунтованого вибору моделі (не «беремо OpenAI бо популярно»)
4. Корпорація може клонувати репо і запустити на своїх даних

### Q5. Якби ти переробляв роботу — що зробив би інакше?

**A:**
1. **Більше запитів** у benchmark (300 → 1500+)
2. **Graded relevance** замість бінарної
3. **Hybrid retrieval** — реалізував би BM25 + BGE-M3 + RRF
4. **Fine-tuning** хоча б BGE-M3 на укр-даних
5. **Більше моделей** — BGE-en, LaBSE, OpenAI text-embedding-3
6. **GPU** — для швидших експериментів

### Q6. Як це впишеться в широкий контекст AI/ML?

**A:** Семантичний пошук — основа **retrieval** компоненти **RAG**. RAG — гаряча тема 2024-2025 (ChatGPT, Perplexity використовують). Якість retrieval — це **bottleneck** якості RAG-систем. Моя робота дає **прикладний фундамент** для побудови RAG: вибір правильної моделі retrieval критично важливий.

### Q7. Хто може використовувати твою систему?

**A:**
1. **Українські корпорації** з великими базами документів (банки, страхові, юридичні фірми)
2. **Університети** — для пошуку по бібліотеках статей
3. **Медичні установи** — для пошуку по клінічним протоколам
4. **Розробники чат-ботів** для замовників-українців
5. **Дослідники** — як starter kit для своїх IR-експериментів

Особливо корисно для тих, у кого є дані, **які не можна** відправляти в OpenAI з причин приватності.

### Q8. Чому ти не виміряв **точність відповіді** в RAG-стилі?

**A:** Бо це **інша задача**. Моя робота — про **retrieval** (знайти правильні документи). Точність відповіді (generation) — це окрема ланка (LLM + промпт). Якість retrieval **впливає** на якість generation, але міряти треба окремо. Перспектива — інтеграція з LLM і повна end-to-end оцінка.

### Q9. Що би ти сказав скептику, який каже «просто беріть OpenAI»?

**A:** Кілька аргументів:
1. **Приватність** — корпоративні дані не можна відправляти в OpenAI
2. **Контроль** — fine-tuning на своїх даних можливий тільки з open-source
3. **Вартість** — на великих обсягах OpenAI API дорогий
4. **Залежність** — vendor lock-in, ризики при змінах ціни/політики
5. **Якість** — моя робота показала, що **open-source альтернативи конкурентні**: BGE-M3 на укр-tech дає nDCG 0.67. Це **достатньо** для більшості сценаріїв.

OpenAI — **простий** вибір, але не **завжди оптимальний**.

### Q10. Як цей висновок ти промовиш на захисті?

**A:**
> «Робота довела статистично значущу перевагу embedding-моделей над лексичним BM25 на українських корпоративних колекціях. Зокрема, BGE-M3 рекомендується як основна модель для впровадження. Для real-time сценаріїв — E5-base. Для юридичних колекцій — Qwen3. Розроблено повнофункціональну веб-систему з інтерактивним багатокритеріальним вибором моделі. Усі поставлені задачі виконано. Мета досягнута.»

Це і є ключове на 30-секундах фінальної промови (слайд 18).
