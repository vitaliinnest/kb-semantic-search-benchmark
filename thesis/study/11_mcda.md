# 11. Лінійна адитивна згортка (MCDA)

> **TL;DR:** MCDA = Multi-Criteria Decision Analysis. У роботі — лінійна адитивна згортка: інтегральна оцінка моделі — це **сума ваг × нормалізованих значень критеріїв**. Найвища U — переможець. Сума ваг = 1. Ваги задає користувач (через профілі домена або вручну). Це **другий крок** після Парето-домінування і дає **остаточну рекомендацію**.

## 1. Постановка задачі MCDA

### Загальна задача

Дано:
- N **альтернатив** (тут — моделі: BGE-M3, E5, ..., BM25)
- K **критеріїв** (тут — nDCG, MRR, Recall, P@10, latency)
- **Значення** кожної альтернативи за кожним критерієм
- **Пріоритети** користувача (через ваги критеріїв)

Знайти: **одну** альтернативу — найкращу.

### Чому не «просто найкраща nDCG»

Бо «найкраща» залежить від багатьох факторів:
- Якщо ще латентність — BM25 може виграти у real-time
- Якщо ще Recall — Qwen3 може виграти в медицині
- Складніше за «один рядок таблиці»

MCDA — це **формалізація** того, як зважено **усі** критерії одночасно.

### Класи MCDA-методів

1. **Скалярні методи** (одна функція корисності) — лінійна згортка, TOPSIS
2. **Outranking методи** — ELECTRE, PROMETHEE
3. **Багатоатрибутна теорія корисності** — MAUT, AHP
4. **Інтерактивні методи** — користувач уточнює пріоритети в процесі

У твоїй роботі — **лінійна адитивна згортка** з класу скалярних.

## 2. Лінійна адитивна згортка — суть

### Формула

```
U(a) = Σⱼ wⱼ · ŷⱼ(a)
```

де:
- `U(a)` — інтегральна оцінка корисності альтернативи a (число)
- `j` — індекс критерію (від 1 до K)
- `wⱼ` — вага j-го критерію (≥0)
- `ŷⱼ(a)` — **нормалізоване** значення j-го критерію для a (в [0, 1])
- Сума: `Σⱼ wⱼ = 1`

### Інтерпретація

«Корисність альтернативи — це **зважене середнє** її значень за всіма критеріями».

Найкраща — та, що максимізує U.

### Чому лінійна

«Лінійна» — функція U лінійна по `ŷⱼ`. Можна було б використати **нелінійні** функції корисності:

```
U(a) = Σⱼ wⱼ · f(ŷⱼ(a))
```

де f — функція. Наприклад, `f(x) = x²` робить високі значення значно ціннішими за низькі.

Але лінійна — **найпростіша**, **найбільш інтерпретовна**, не вимагає додаткових припущень про функцію корисності.

### Чому адитивна

«Адитивна» — критерії **складаються** (а не множаться). Альтернатива: мультиплікативна:
```
U(a) = Πⱼ ŷⱼ(a)^wⱼ
```

Мультиплікативна штрафує сильніше: якщо одне значення = 0, U = 0. Адитивна — компенсує: інші високі значення піднімають загальний U.

У роботі — **адитивна**, бо немає категоричних «обов'язкових» критеріїв (всі важливі, але жодне не має значення «без чого ніяк»).

## 3. Нормалізація: чому і як

### Проблема

Критерії мають **різні шкали**:
- nDCG ∈ [0, 1]
- Латентність ∈ [0.4, 463] мс

Якщо сумувати «сировi» — латентність буде **домінувати** через великі числа:

```
U(BGE) = 0.30 × 0.6722 + 0.20 × 222.5 = 0.20 + 44.50 = 44.70
U(BM25) = 0.30 × 0.4861 + 0.20 × 0.4 = 0.146 + 0.08 = 0.226
```

Хто **виграв за U**? BGE — бо латентність 222.5 в **сотні разів** більша за nDCG. Незалежно від ваг.

**Це абсурд** — латентність на мінімізацію, але через сирі числа стала найважливішим критерієм.

### Розв'язання: нормалізація

Привести **всі** критерії до **однієї шкали** [0, 1], з **єдиним напрямком** (1 = найкраще).

### Min-max нормалізація

Найпростіший і найпоширеніший метод:

Для критеріїв на **максимізацію** (nDCG, MRR, Recall, P@10):
```
ŷ = (x − min) / (max − min)
```

Для критеріїв на **мінімізацію** (latency):
```
ŷ = (max − x) / (max − min)
```

де `min` і `max` — мінімум і максимум критерію серед всіх альтернатив.

### Приклад нормалізації (tech-домен)

**nDCG (max):** значення [0.3765, 0.4861, 0.6121, 0.6325, 0.6722].
- min = 0.3765, max = 0.6722
- BGE-M3: (0.6722 - 0.3765) / (0.6722 - 0.3765) = **1.0**
- Qwen3: (0.6325 - 0.3765) / 0.2957 = **0.866**
- E5: (0.6121 - 0.3765) / 0.2957 = **0.797**
- BM25: (0.4861 - 0.3765) / 0.2957 = **0.371**
- nomic: (0.3765 - 0.3765) / 0.2957 = **0.0**

**Латентність (min):** значення [0.4, 70.9, 124.8, 222.5, 463.4].
- min = 0.4, max = 463.4
- BM25: (463.4 - 0.4) / (463.4 - 0.4) = **1.0**
- E5: (463.4 - 70.9) / 463.0 = **0.848**
- nomic: (463.4 - 124.8) / 463.0 = **0.731**
- BGE-M3: (463.4 - 222.5) / 463.0 = **0.520**
- Qwen3: (463.4 - 463.4) / 463.0 = **0.0**

Тепер усі — в [0, 1], 1 = найкраще.

### Інші методи нормалізації

| Метод | Формула | Коли |
|---|---|---|
| **Min-max** | `(x - min) / (max - min)` | Найпоширеніший. Чутливий до викидів. |
| **Z-score** | `(x - μ) / σ` | Якщо хочеш центрувати; не обмежений [0,1] |
| **Vector** | `x / ||x||` | Зберігає пропорції; **L2 нормалізація** |
| **Max** | `x / max` | Спрощений min-max |

У роботі — **min-max**. Це стандарт у MCDA-літературі.

## 4. Ваги: як обираються

### Властивості

- `wⱼ ≥ 0` — невід'ємні
- `Σⱼ wⱼ = 1` — сума 1 (нормалізовані ваги)

Якщо ваги не нормалізовані — можна привести: `w'ⱼ = wⱼ / Σ wⱼ`.

### Методи призначення ваг

1. **Експертне призначення** (твій метод):
   - Експерт каже: «у моєму домені nDCG важливіше за швидкодію в 1.5 рази»
   - Призначає ваги «з голови»
   - Швидко, але суб'єктивно

2. **AHP (Analytic Hierarchy Process):**
   - Попарне порівняння всіх критеріїв
   - Розрахунок ваг через власні вектори матриці
   - Більш строгий, але складніший

3. **Entropy method:**
   - Ваги визначаються через ентропію критеріїв
   - Об'єктивний, без думки експерта
   - Іноді дає дивні результати

4. **Зворотна задача:**
   - Користувач задає рейтинг альтернатив, ваги дораховуються
   - Корисно для navigation

5. **Sensitivity analysis** (наступний розділ) — перевірка стійкості до зміни ваг.

### Інтерпретація ваг

```
nDCG = 0.30
MRR = 0.20
Recall = 0.25
P@10 = 0.05
latency = 0.20
```

«nDCG найважливіший, його значення в загальному score рахується в **1.5 рази** вагоміше, ніж latency».

## 5. Профілі ваг по доменах

У твоєму застосунку — **3 профілі** + дефолт.

### Технічний (балансовий)

```
nDCG = 0.30
MRR = 0.20
Recall = 0.25
P@10 = 0.05
latency = 0.20
```

**Логіка:**
- nDCG — головне якість
- MRR — позиція перших важлива
- Recall — повнота важлива
- P@10 — менш важлива (мало релевантних на запит)
- latency — відчутно важлива (часто real-time)

### Юридичний (priority on MRR)

```
nDCG = 0.30
MRR = 0.30  ← підвищено
Recall = 0.20
P@10 = 0.10  ← підвищено
latency = 0.10  ← знижено
```

**Логіка:**
- MRR підвищено: юристу критично — **швидко знайти ПЕРШИЙ** правильний документ
- P@10 підвищено: чиста видача важлива (юрист не хоче гортати)
- Latency знижено: юрист може зачекати кілька секунд

### Медичний (priority on Recall)

```
nDCG = 0.25
MRR = 0.15  ← знижено
Recall = 0.35  ← найвища вага
P@10 = 0.10  ← підвищено
latency = 0.15  ← між
```

**Логіка:**
- Recall критично — **не пропустити** релевантне (життя пацієнта)
- MRR знижено: лікар може переглянути кілька результатів
- P@10 — чистота видачі помічна, але не критична
- Latency — помірна

### Дефолт

```
nDCG = 0.30
MRR = 0.25
Recall = 0.25
P@10 = 0.10
latency = 0.10
```

Балансовий для випадків, коли домен не обрано.

## 6. Чому саме ці ваги

Це **запитання, яке обов'язково буде на захисті**. Готова відповідь:

### Емпіричне обґрунтування

Ваги підібрано **експертно** на основі **специфіки кожного домена**:

- **Tech:** загальний пошук документації — баланс критеріїв
- **Legal:** юрист працює з ідентифікованими документами, тому критично **позиція першого** релевантного — MRR. Швидкодія менш критична — юрист готовий чекати.
- **Medical:** недопустимо **пропустити релевантне** (помилка може коштувати життя) — Recall пріоритет. Швидкість прийнятна.

### Альтернативні обґрунтування

1. **AHP** — можна було б використати, але вимагає попарних порівнянь у експертів. У моїй роботі — спрощений підхід, описаний у розділі 5.3.5 записки.
2. **Користувацькі ваги:** у застосунку є слайдери — користувач може **сам** змінити ваги і подивитись, як змінюється рекомендація.

### Sensitivity analysis (наступний розділ)

Перевірка: «якщо ваги змінити на ±10%, чи зміниться рекомендація?» У більшості випадків — ні (BGE-M3 залишається лідером). Це підтверджує **робастність** системи.

## 7. Чутливість до ваг

### Що це таке

Перевірка: **наскільки рекомендація залежить від конкретних ваг**. Якщо ваги змінити трохи — чи поміняється лідер?

### Як перевіряти

1. **Locally:** змінити одну вагу на ±5-10%, подивитись.
2. **Globally:** систематично варіювати всі ваги в діапазоні.

### У застосунку

`/benchmark/selection?domain=tech` — слайдер latency. Зміни від 0.20 до 0.50:
- При 0.20 (тech профіль) — рекомендація: BGE-M3
- При 0.30 — все ще BGE-M3
- При 0.40 — починає змінюватись
- При 0.50 — рекомендація: **E5-base**

Це показує: при **помірних змінах** ваг BGE-M3 стабільно лідер. При **сильних змінах** (latency важливіше за nDCG) — E5 переходить вперед.

### Висновок

Система **стійка** при типових налаштуваннях. Лише при кардинальній зміні пріоритетів (real-time-критичність) рекомендація змінюється.

Це **демонструє** силу MCDA: дає **стабільну** рекомендацію для розумних пріоритетів, але **слухається** користувача, якщо пріоритети змінюються кардинально.

## 8. Альтернативи MCDA

### TOPSIS

Technique for Order of Preference by Similarity to Ideal Solution.

Алгоритм:
1. Нормалізація (як у нас)
2. Зважування (як у нас)
3. **Знаходимо «ідеальну» точку** (max по всім критеріям) і «анти-ідеальну» (min по всім)
4. Для кожної альтернативи: **відстань** до ідеала і анти-ідеала
5. Score: `D⁻ / (D⁺ + D⁻)` — близкість до ідеала

**Плюси:** робастна; враховує не лише «середнє», а й «найгірший» критерій.
**Мінуси:** вимагає вибору метрики відстані; складніша.

### AHP (Analytic Hierarchy Process)

Метод попарного порівняння.

1. Експерт каже: «nDCG vs MRR — у X разів важливіше»
2. Будує матрицю порівнянь
3. Власні вектори дають ваги
4. Послідовність перевіряється через consistency ratio

**Плюси:** строгий, перевіряє несуперечність думок.
**Мінуси:** трудомісткий (десятки попарних порівнянь).

### ELECTRE / PROMETHEE

Outranking методи. Замість «однієї згортки» — пара pair-wise тестів: чи альтернатива A «достатньо краща» за B за всіма критеріями?

**Плюси:** не вимагає нормалізації; ловить категоричні відмінності.
**Мінуси:** складна інтерпретація; багато параметрів.

### Чому лінійна згортка у твоїй роботі

1. **Простота** — легко пояснити, легко реалізувати
2. **Інтерпретовність** — користувач бачить, як кожна вага впливає на score
3. **Гнучкість** — користувач може змінити ваги в реальному часі (через UI)
4. **Стандарт у IR** — багато публікацій використовують лінійну згортку
5. **Не вимагає попарних порівнянь** (на відміну від AHP)

Якби обрав TOPSIS — додатковий шар складності, але якісно не далекий від результат. Якби AHP — рекомендація буде та сама, але реалізація складніша.

**BGE-M3:** 0.15·1.0 + 0.10·1.0 + 0.15·1.0 + 0.10·1.0 + 0.50·0.520 = 0.50 + 0.26 = **0.76**
**E5-base:** 0.15·0.797 + 0.10·0.770 + 0.15·0.902 + 0.10·0.901 + 0.50·0.848 = 0.12+0.077+0.135+0.09+0.424 = **0.846**
**BM25:** 0.15·0.371 + 0.10·0.241 + 0.15·0.825 + 0.10·0.872 + 0.50·1.0 = 0.056+0.024+0.124+0.087+0.5 = **0.791**

**Новий лідер: E5-base** (0.846 > BGE 0.76 > BM25 0.791).

Це **той самий результат**, що показано у демо-відео (section 4) — slider latency = 0.50 → recommendation flips to E5-base.

## 11. Перевірочні питання з відповідями

### Q1. Що станеться зі score, якщо забути нормалізувати критерії перед сумуванням?

**A:** Латентність (значення 0-500) у **сотні разів більше** за nDCG (0-1). Сума буде **домінована латентністю**, незалежно від ваг. Результат: модель з найвищою латентністю **виграє** (по сирим числам), що абсурд (бо latency на мінімізацію). Нормалізація приводить усі критерії до [0, 1] з єдиним напрямком — це **критичний** крок.

### Q2. Чому вага сумарно = 1, а не довільна?

**A:** Це **математична конвенція**. Якщо ваги в сумі = 1, то U(a) знаходиться в тому ж діапазоні, що і ŷⱼ (нормалізовано). Інакше — U зростає лінійно з сумою ваг, без додаткового сенсу. Сума 1 — стандарт у MCDA-літературі.

### Q3. Чи може лінійна згортка обрати модель, яка **не** в Парето-множині?

**A:** **Ні**. Якщо альтернатива A домінується іншою B (A гірша скрізь), то для **будь-яких невід'ємних ваг** U(B) ≥ U(A). Лінійна згортка ніколи не обере домінованого. Тому Парето-фільтр — **необов'язковий крок** перед згорткою, але **корисний** для інтерпретації.

### Q4. Опиши інший MCDA-метод і скажи, чому в роботі обрали саме лінійну згортку.

**A:** **TOPSIS** — знаходить «ідеальну точку» (max по всіх критеріях) і «анти-ідеальну» (min). Кожна альтернатива оцінюється за **близькістю** до ідеала і анти-ідеала. Score = `D⁻/(D⁺+D⁻)`. **Плюс:** робастніший, враховує не лише «середнє». **Мінус:** складніший в інтерпретації.

У моїй роботі — **лінійна згортка** через простоту і прозорість. Користувач явно бачить, як кожна вага впливає на оцінку. Це **інтерпретовно** і легко пояснити комісії. TOPSIS і AHP — згадані як альтернативи, але обрана згортка через **прозорість**.

### Q5. Як ваги впливають на остаточний вибір?

**A:** Ваги — це **зважування критеріїв за пріоритетами користувача**. Якщо вага nDCG висока (0.5), модель з найкращим nDCG виграє навіть якщо повільна. Якщо вага latency висока (0.5) — швидка модель виграє. Через **слайдери в UI** користувач може експериментувати — це **інтерактивна MCDA**.

### Q6. Що означає «домен-специфічний профіль ваг»?

**A:** Це **попередньо налаштовані** ваги, призначені для типового сценарію в конкретному домені. У моїй роботі:
- **Tech:** баланс (всі ваги помірні)
- **Legal:** пріоритет MRR (швидко знайти першу статтю)
- **Medical:** пріоритет Recall (не пропустити релевантне)

Користувач може почати з профіля і потім **тонко настроїти** через слайдери.

### Q7. Якщо я хочу, щоб система рекомендувала E5-base — як налаштувати ваги?

**A:** Підвищити **latency** (на якому E5 виграє BGE) і знизити **nDCG/MRR** (де BGE сильніший). Наприклад: latency = 0.50, інші ≈ 0.10-0.15. Після перерахунку E5-base буде лідером. Це і демонструється у демо-відео.

### Q8. Що, якщо ваги задані як 0.7 + 0.2 + 0.3 (сума 1.2)?

**A:** Нормалізую їх: w'ⱼ = wⱼ / Σwⱼ → (0.583, 0.167, 0.250). Сума = 1. Це **внутрішнє виправлення**: користувач може думати в довільних числах, система нормалізує. У коді — `normalize_weights()`.

### Q9. Лінійна згортка завжди дає чітку відповідь?

**A:** Майже завжди. **Виняток:** якщо дві моделі мають **однаковий** U (рідко). Тоді відповідь не унікальна. У моїй роботі — таких ситуацій не виявлено, бо моделі мають значущі відмінності.

### Q10. Як цей крок поєднується з Парето?

**A:** Парето — **відсів** домінованих альтернатив. Лінійна згортка — **вибір однієї** з Парето-альтернатив. **Двокроковий процес:**
1. Парето: 5 моделей → 3 раціональних (Tech: {BGE, E5, BM25})
2. Лінійна згортка з вагами → 1 переможець (Tech: BGE-M3)

Парето сам **не дає** одну відповідь — лише фільтрує. Згортка з вагами завершує процес. У застосунку обидва кроки показані: «Парето-множина» (плашки) і «Рекомендована модель» (з score) — наочно бачиш обидва результати.
