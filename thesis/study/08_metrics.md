## 1. Чому одного числа недостатньо

Якість пошуку — складна штука. Один запит, система повернула 10 документів. Як оцінити?

Ось 3 сценарії з різними «помилками»:

**Сценарій А.** Релевантний документ на **1-му** місці, інші 9 — нерелевантні.
**Сценарій Б.** Релевантний документ на **10-му** місці, інші 9 — нерелевантні.
**Сценарій В.** Усі 10 — релевантні.

Якщо рахувати «**знайшли релевантне?**» — усі троє кажуть «так». Це **insufficient**.

Деталі:
- В **А** — користувачу зручно: перший клік дав відповідь.
- В **Б** — користувач довго гортав. Гірше за А.
- В **В** — взагалі весь топ. Можливо краще, ніж А (якщо тематика складна і є кілька правильних). Або гірше, якщо шукав одну конкретну.

Тому в IR використовують **набір метрик**, кожна вимірює свій аспект:

| Метрика | Що цінує | Що ігнорує |
|---|---|---|
| nDCG | і факт релевантності, **і позиція** | — |
| MRR | позиція **першого** релевантного | другий, третій |
| Recall | **скільки** з усіх релевантних знайдено | позицію |
| Precision | **чистоту** видачі (% релевантних) | повноту |

## 2. Базова ідея: ground truth і qrels

### Що таке qrels

**qrels** = query relevance judgments. Це **експертна розмітка**: для кожного запиту — список релевантних документів (або чанків).

Приклад з твого репо (`data/domains/tech/benchmark/qrels.jsonl`):
```json
{"query_id": "q1", "doc_id": "doc_001", "relevance": 1}
{"query_id": "q1", "doc_id": "doc_005", "relevance": 1}
{"query_id": "q2", "doc_id": "doc_003", "relevance": 1}
...
```

Для запиту q1 релевантні документи doc_001 і doc_005. Для q2 — doc_003.

**relevance** — зазвичай 1 (бінарна релевантність). Може бути 2, 3 для **graded relevance** (трохи релевантне, дуже релевантне). У тебе — переважно бінарна.

### Як qrels впливає на метрики

Метрики порівнюють результат пошуку з qrels. Наприклад:
- Пошук повернув: `[doc_002, doc_005, doc_007, doc_001, ...]`
- qrels кажуть: doc_001 і doc_005 релевантні
- На якій позиції релевантні? doc_005 на 2-й, doc_001 на 4-й
- Це і є вхід у формули метрик

### У твоїй роботі

- **300 запитів** загалом (100 на домен)
- **~3-5 релевантних** на запит у середньому
- qrels **сформовано вручну** — найдорожча частина роботи

## 3. nDCG@k — головна метрика

### Повна назва

**n**ormalized **D**iscounted **C**umulative **G**ain — «нормалізована дисконтована кумулятивна вигода».

### Інтуїція

Користувач отримав видачу — «отримує **вигоду**» від кожного релевантного документа. Але документи нижче — гірше (треба гортати). Тому вигода **дисконтується** (зменшується) залежно від позиції.

### Формули

#### DCG@k (без нормалізації)

```
DCG@k = Σᵢ₌₁ᵏ (2^relᵢ − 1) / log₂(i + 1)
```

де:
- `relᵢ` — релевантність документа на позиції i (0 = нерелевантний, 1 = релевантний)
- `log₂(i + 1)` — дисконт по позиції

**Чому log₂(i+1):** так щоб для позиції 1 ділили на log₂(2) = 1 (повна вага), для позиції 2 — на log₂(3) ≈ 1.585 (трохи менше), для позиції 10 — на log₂(11) ≈ 3.46 (значно менше). **Плавне** падіння ваги з позицією.

#### IDCG@k (ідеальне DCG)

DCG для **найкращого можливого** ранжування — коли всі релевантні документи зверху.

```
IDCG@k = Σᵢ₌₁ᵏ (2^rel*ᵢ − 1) / log₂(i + 1)
```

де `rel*ᵢ` — релевантність на позиції i при **ідеальному** ранжуванні.

#### nDCG@k

```
nDCG@k = DCG@k / IDCG@k
```

Завжди в [0, 1]. **1 = ідеально**, 0 = в топ-k немає жодного релевантного.

### Чому **n**ormalized

DCG залежить від кількості релевантних документів. Запит з 10 релевантними має набагато більший DCG, ніж запит з 1 релевантним. Нормалізація (поділ на IDCG) **робить метрику порівняльною** між запитами з різною кількістю релевантних.

### Особливість

nDCG **враховує і факт релевантності, і позицію** — це і є його перевага. Інші метрики або ігнорують позицію (Recall, Precision), або дивляться тільки на першу (MRR).

### Приклад

Запит. Релевантні: doc_A, doc_B.

**Видача 1:** `[doc_A, doc_B, doc_C, ...]` (релевантні на 1, 2)
DCG = 1/log₂(2) + 1/log₂(3) = 1.0 + 0.631 = 1.631
IDCG (ідеал = той самий) = 1.631
nDCG = **1.0** (ідеально)

**Видача 2:** `[doc_C, doc_A, doc_D, doc_B, ...]` (релевантні на 2, 4)
DCG = 0 + 1/log₂(3) + 0 + 1/log₂(5) = 0.631 + 0.431 = 1.062
IDCG = 1.631 (так само)
nDCG = 1.062 / 1.631 ≈ **0.651**

**Видача 3:** `[doc_C, doc_D, doc_E, ..., doc_A, doc_B]` (релевантні на 9, 10)
DCG = 1/log₂(10) + 1/log₂(11) = 0.301 + 0.289 = 0.590
nDCG = 0.590 / 1.631 ≈ **0.362**

Бачиш: чим нижче позиції релевантних — тим менше nDCG. **Розуміє позицію**.

## 4. MRR — позиція першого релевантного

### Повна назва

**M**ean **R**eciprocal **R**ank — середній обернений ранг.

### Формула

Для одного запиту q:
```
RR(q) = 1 / rank(перший релевантний у видачі)
```

Для набору запитів:
```
MRR = (1/|Q|) · Σ RR(q)
```

### Приклади

- Перший релевантний на **позиції 1** → RR = 1/1 = **1.0**
- Перший релевантний на **позиції 3** → RR = 1/3 ≈ **0.333**
- Перший релевантний на **позиції 10** → RR = 1/10 = **0.1**
- **Жодного релевантного** в топ-10 → RR = 0 (домовленість)

### Особливість

MRR **ігнорує** все, крім **першого** релевантного. Запит з 5-ма релевантними, де перший на позиції 2 — той самий RR=0.5, що і запит з 1-м релевантним на позиції 2.

### MRR@k vs MRR без обмеження

Зазвичай у роботі — MRR@k (тобто шукаємо перший релевантний серед топ-k). У тебе k=10. Якщо перший релевантний знайдеться лише на позиції 15 — RR = 0 для MRR@10.

### Коли MRR корисний

- Тут користувач хоче **швидко знайти першу відповідь** і піти. Наприклад, юристу — знайти першу релевантну статтю кодексу.
- На юридичному домені MRR має **вищу вагу** у MCDA (профіль legal: MRR=0.30 vs 0.20 на tech).

## 5. Recall@k — повнота

### Інтуїція

«Скільки з усіх релевантних документів я знайшов?»

### Формула

```
Recall@k = |Rel ∩ Retrieved@k| / |Rel|
```

де:
- `Rel` — усі релевантні документи (з qrels)
- `Retrieved@k` — топ-k результатів пошуку

### Приклад

Запит. У qrels — 5 релевантних: {A, B, C, D, E}.

Видача топ-10: `[A, X, B, Y, Z, D, W, V, U, T]`

Знайдено релевантних серед топ-10: A, B, D = 3.
Recall@10 = 3 / 5 = **0.6**

### Особливість

Recall **не дивиться на позицію**. Якщо релевантний на 1-му чи на 10-му — однаково внесок в Recall.

### Коли важлива

**Сценарій повноти:** медицина, юриспруденція — недопустимо пропустити релевантне. Краще додати кілька нерелевантних, але показати все, що може бути корисним.

Тому в моделі **medical** профіль ваг MCDA: Recall=0.35 (найвища вага).

### Recall vs Precision: trade-off

Recall можна тривіально збільшити — повертай **всі** документи. Тоді Recall = 1.0. Але Precision = `|Rel|/N` — крихітна.

Тому ці дві метрики дивляться разом.

## 6. Precision@k — точність

### Інтуїція

«Серед перших k результатів, скільки релевантних?»

### Формула

```
P@k = |Rel ∩ Retrieved@k| / k
```

### Приклад (той самий)

Запит. Релевантні: {A, B, C, D, E}.
Видача топ-10: `[A, X, B, Y, Z, D, W, V, U, T]`

Серед топ-10 — 3 релевантних.
P@10 = 3 / 10 = **0.3**

### Особливість

Знаменник **завжди k** (тут — 10). Не залежить від кількості релевантних у корпусі.

Якщо у корпусі **тільки 1 релевантний** для запиту, максимально можлива P@10 = 1/10 = **0.1** (10% — це найкращий результат). Це обмеження «по-конструкції».

### Коли важлива

**Сценарій чистоти:** користувач не буде гортати, дивиться топ-3. Хоче, щоб ці 3 — всі релевантні.

### Чому P@10 у моделі tech має малу вагу (0.05)?

Бо у тебе на запит зазвичай **мало релевантних** (3-5). Тому P@10 максимально досягне 0.5 — не 1.0. Метрика **обмежена за конструкцією** і менш інформативна. На це і Mрахун невелика вага.

## 7. Повний worked example

Розберемо все на одному запиті. Тренувальний приклад.

### Дано

Запит: «що таке Python»

У qrels — 3 релевантних документи: **A, B, C**.

Модель повернула топ-5: **[A, X, B, Y, Z]**, де X, Y, Z — нерелевантні.

### nDCG@5

DCG@5:
- pos 1: A релевантний → (2^1 − 1) / log₂(2) = 1/1 = **1.0**
- pos 2: X нерелевантний → 0
- pos 3: B релевантний → (2^1 − 1) / log₂(4) = 1/2 = **0.5**
- pos 4: Y нерелевантний → 0
- pos 5: Z нерелевантний → 0

DCG@5 = 1.0 + 0 + 0.5 + 0 + 0 = **1.5**

IDCG@5 (ідеал: всі 3 релевантні на верху):
- pos 1: A → 1.0
- pos 2: B → 1/log₂(3) = 0.631
- pos 3: C → 1/log₂(4) = 0.5
- pos 4-5: нічого більше релевантного → 0

IDCG@5 = 1.0 + 0.631 + 0.5 = **2.131**

nDCG@5 = 1.5 / 2.131 ≈ **0.704**

### MRR

Перший релевантний у видачі — A на позиції 1.
RR = 1/1 = **1.0**

Якщо у тебе кілька запитів — MRR = середнє RR.

### Recall@5

Знайдено 2 релевантних (A, B) з 3 загалом.
Recall@5 = 2/3 ≈ **0.667**

### Precision@5

Знайдено 2 релевантних з 5 топ-результатів.
P@5 = 2/5 = **0.4**

### Інтерпретація

| Метрика | Значення | Що каже |
|---|---|---|
| nDCG | 0.704 | Загалом непогано: знайдено 2 з 3 релевантних, на хороших позиціях |
| MRR | 1.0 | Ідеально — перший релевантний на 1-му місці |
| Recall | 0.667 | Знайдено 2/3 — норм, але можна краще |
| P@5 | 0.4 | З 5 результатів — 2 релевантних, тобто 40% видачі — релевантна |

### Що якби ранжування було гіршим

Видача: `[X, Y, A, B, Z]` (релевантні на 3, 4)

- nDCG@5: DCG = 1/log₂(4) + 1/log₂(5) = 0.5 + 0.431 = 0.931. nDCG = 0.931 / 2.131 ≈ **0.437**
- MRR: 1/3 ≈ **0.333**
- Recall@5: 2/3 ≈ **0.667** (та сама — кількість знайдених не змінилась)
- P@5: 2/5 = **0.4** (та сама)

Що цікаво:
- **nDCG значно впав** (0.704 → 0.437) — бо позиція важлива
- **MRR значно впав** (1.0 → 0.333) — бо перший релевантний на 3-й позиції
- **Recall той же** — кількість знайдених релевантних не змінилась
- **P@5 той же** — те саме

Це показує, що **nDCG і MRR — чутливі до позиції**, Recall і P@k — ні.

## 8. Інші метрики (MAP, ARP)

Для довідки і Q&A.

### MAP — Mean Average Precision

Для одного запиту:
```
AP(q) = (1/|Rel|) · Σ_k P@k × rel_k
```

де `rel_k` = 1, якщо документ на позиції k релевантний, 0 інакше.

Тобто **середнє P@k по всіх позиціях релевантних документів**.

MAP — середнє AP по запитах.

**Інтерпретація:** як nDCG, але працює тільки з бінарною релевантністю. Менш гнучкий.

**Чому в твоїй роботі не використано:** nDCG **строгіша** для graded relevance. MAP — стандарт у TREC-стилі, але nDCG — у сучасних benchmarks.

### ARP — Average Reciprocal Position

Майже те саме, що MRR, але враховує всі релевантні, а не тільки перший.

### F1@k

Гармонічне середнє Precision@k і Recall@k.

```
F1 = 2 × (P × R) / (P + R)
```

**Інтерпретація:** баланс P і R. У літературі іноді використовують.

**Чому не в твоїй роботі:** Recall і Precision окремо інформативніші. F1 — комбінований показник, втрачає деталь.

## 9. Як обирати k

### Чому @10

У сучасній IR-літературі @10 — **стандарт за замовчуванням**. Причини:
- Користувач рідко гортає за 10-у сторінку результатів
- @5 — занадто короткий зріз для оцінки повноти
- @20 — користувач не дивиться так глибоко

### Чи можна @5 або @20

Так, але обирай **один** для всієї роботи. Інакше — порівняння нечесне.

У тебе всюди @10:
- nDCG@10
- MRR@10
- Recall@10
- P@10

Це **узгоджено**.

### Що, якщо я хочу @1 (тільки перший результат)

P@1 ∈ {0, 1} — тільки два значення. Замало для агрегації.
nDCG@1 = 1, якщо перший релевантний; 0 — інакше. Те саме обмеження.

@5 чи @10 — кращі для статистики.

## 11. Перевірочні питання з відповідями

### Q1. Який практичний сенс має «дисконт» у nDCG?

**A:** Дисконт — це поділ на `log₂(позиція + 1)`. Він **зменшує внесок** релевантних документів на нижчих позиціях. Сенс: користувачу гірше, коли треба гортати — метрика це **формалізує**.

### Q2. Може nDCG бути меншою за Recall? Поясни.

**A:** Так. Recall дивиться лише на **кількість** знайдених релевантних. nDCG ще враховує **позицію**. Якщо релевантні на низьких позиціях (наприклад, 8-10 з 10), Recall@10 буде висока (всі знайдені), але nDCG@10 — низька (вага позицій 8-10 мала).

### Q3. Чому в роботі обрано саме @10, а не @5 чи @20?

**A:** **@10 — стандарт у сучасній IR-літературі**. Користувач рідко гортає за 10-у сторінку, тому це релевантний зріз. @5 — занадто короткий для надійної оцінки (мало data points). @20 — користувач так глибоко не дивиться. Обрано @10 і застосовано до **всіх** метрик однаково для узгодженості.

### Q4. Якщо в корпусі тільки 1 релевантний документ на запит — Recall@10 і P@10 як співвідносяться?

**A:** Якщо документ знайдено в топ-10:
- Recall@10 = 1/1 = **1.0** (знайшли все, що було)
- P@10 = 1/10 = **0.1** (1 з 10 — релевантний)

Це принципово: P@10 **обмежений** кількістю релевантних у корпусі. Recall не обмежений (завжди можна досягти 1.0).

### Q5. Якщо я бачу високий MRR, але низький Recall — що це значить?

**A:** Модель **знаходить перший** релевантний документ хорошо (MRR високий, перший на позиції 1-2). Але **пропускає інші релевантні** (Recall низький). Це типова поведінка для precision-oriented моделей. Корисна, коли потрібно «швидко знайти першу відповідь». Гірша, коли потрібен повний огляд (медицина).

### Q6. Чи можна отримати nDCG = 1.0?

**A:** Так — якщо ВСІ релевантні документи з qrels — на ТОП позиціях (на найвищих можливих). Тобто перший в індексі релевантний — на 1-му місці, другий — на 2-му, і т.д. У реальності — рідко, але можливо для простих запитів з 1 чітким релевантним.

### Q7. Чому в твоїй роботі MAP не використовується?

**A:** Бо **nDCG строгіша** для оцінки якості ранжування. MAP — стандарт у TREC-style benchmarks 1990-х. Сучасні MTEB, BEIR використовують nDCG. Крім того, MAP працює лише з бінарною релевантністю, nDCG — і з graded. У майбутньому, якщо додам graded relevance в qrels — nDCG це підтримає, MAP — ні.

### Q8. Що буде з метриками, якщо я викину половину релевантних з qrels?

**A:** Великі зміни. **Recall** — буде вищим штучно (бо ділимо на меншу |Rel|). **Precision** — той же (k фіксований). **MRR** — той же (перший знайдений залишається). **nDCG** — теж зміниться через нове IDCG. Тому **якість qrels критична** — спотворення розмітки → спотворення метрик.

### Q9. Який зв'язок між nDCG та DCG?

**A:** DCG (без n) — некроме значення. Залежить від кількості релевантних: запит з 10 релевантними матиме більший DCG, ніж з 1. Це робить **DCG непорівняним** між запитами з різною кількістю релевантних. nDCG **нормалізує** через ділення на IDCG (ідеальне DCG). Тепер усі запити порівняні: 0 — погано, 1 — ідеально.

### Q10. Як ти будеш аргументувати вибір саме цих 4 метрик на захисті?

**A:** Усі 4 — **стандарт у IR-літературі**. Кожна вимірює різний аспект:
- nDCG — головна, враховує і факт, і позицію (graded-friendly)
- MRR — позиція першого релевантного (важливо для precision-критичних сценаріїв)
- Recall@10 — повнота (важливо для медичних і юридичних застосувань)
- Precision@10 — чистота видачі (важливо для UX)

Усі застосовуються в комбінації, бо одна метрика не може охопити повну картину. У MCDA вони об'єднуються через ваги відповідно до пріоритетів домена.
