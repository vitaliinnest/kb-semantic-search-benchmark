# 06. Чанкінг — як ділити документи

> **TL;DR:** Чанкінг — це розрізання документа на менші фрагменти (~600 слів) перед індексацією. Потрібен, бо: (1) embedding-моделі мають ліміт контексту (512-32K токенів); (2) вектор цілого документа втратить специфічність. У твоїй роботі — fixed-size з overlap ~80 слів. Стратегія однакова для всіх моделей — це принципово для чесного порівняння.

## 1. Навіщо взагалі чанкінг

### Проблема: довгі документи

Документ — 100 сторінок, ~50,000 слів. Чи можна закодувати його в **один вектор**?

**Технічно:** ні, для більшості моделей.

| Модель | Max контекст (токенів) | Приблизно слів |
|---|---|---|
| BERT base | 512 | ~380 |
| E5-base | 512 | ~380 |
| BGE-M3 | 8192 | ~6000 |
| nomic | 8192 | ~6000 |
| Qwen3 | 32 768 | ~24000 |
| GPT-4 | 128K | ~96000 |

Навіть «довгі» моделі обмежені 6-24K слів. 50K-словний документ **не вміститься**.

### Проблема: семантичне розмиття

Навіть якби можна було закодувати — один вектор для 100 сторінок різного контенту **не несе специфічного сенсу**. Він буде «середнім» по всьому документу.

Запит «протипоказання бета-блокаторів» поверне документ цілком, але **не вкаже**, на якій сторінці є відповідь. Користувачу доведеться шукати руками.

### Розв'язання: чанки

Розрізаємо документ на **самостійні смислові одиниці** (~600 слів). Кожен чанк індексується окремо. При пошуку повертаємо **конкретний чанк**, не весь документ.

```
Документ "Кардіологічний посібник" (50K слів)
    ↓ чанкінг ↓
Чанк 1 (600 слів) — про серцеву анатомію
Чанк 2 (600 слів) — про ЕКГ
...
Чанк 80 (600 слів) — про бета-блокатори ← знайдеться для запиту
...
```

## 2. Стратегія в твоїй роботі

### Параметри

- **min_words:** 300
- **max_words:** 800
- **target:** ~600
- **overlap:** 80 слів

### Алгоритм (приблизно)

```python
def chunk_document(text, min_w=300, max_w=800, overlap=80):
    words = text.split()
    chunks = []
    i = 0
    while i < len(words):
        chunk_end = min(i + 600, len(words))
        chunk = words[i:chunk_end]
        if len(chunk) >= min_w:
            chunks.append(" ".join(chunk))
        i = chunk_end - overlap   # перекриття 80 слів
    return chunks
```

### У коді

`src/ingest_chunk.py` — функція `ingest_chunks()`. Приймає `min_words`, `max_words`, `overlap`.

Приклад виклику:
```python
ingest_chunks(
    input_dir=Path("data/domains/tech/raw"),
    output_file=Path("data/domains/tech/chunks.jsonl"),
    min_words=300,
    max_words=800,
    overlap=80,
)
```

Результат — файл `chunks.jsonl`, кожен рядок:
```json
{"doc_id": "doc_001", "chunk_id": "doc_001_chunk_005", "text": "...", "source": "filename.pdf"}
```

### Параметри в UI

На сторінці `/raw` є форма «Запустити чанкінг», де можна задати ці параметри. Дефолти — min=300, max=800, overlap=80.

## 3. Чому 600 слів

Це **інженерний компроміс**. Розглянемо альтернативи:

### Дуже малі чанки (50-100 слів)

**Плюси:**
- Кожен чанк — точкова інформація
- Висока специфічність вектора

**Мінуси:**
- Контекст втрачений: «Він каже про це» — про що «це»?
- Багато чанків → великий індекс
- Багато результатів → користувач губиться

### Малі чанки (200-300 слів)

- ~1-2 абзаци
- Зазвичай самодостатня одиниця
- Працює добре, але **граничні** для деяких моделей

### Середні чанки (500-700 слів) — твій вибір

- ~1 розділ або 2-3 абзаци
- Самодостатньо
- Добре для всіх 4 моделей (навіть E5-base з 512 токенів — поміщається, бо ~600 слів = ~800-1000 токенів; truncation мінімальний)

### Великі чанки (1500-3000 слів)

- ~1 глава
- Може втратити специфічність (як обговорено вище)
- Не вміщається в E5-base (truncation активна)

### Дуже великі (5000+ слів)

- ~5-10 сторінок
- Втрачає сенс семантичного пошуку (вектор «середнього на сторінку»)
- Не вміщається в більшість моделей

### Чому 600 — оптимальний компроміс для твоєї роботи

1. **Самодостатньо** для типових тем (1 концепція = ~1 чанк)
2. **Вміщається** в усі 4 моделі без значного truncation
3. **Менше чанків** → індекс компактний → швидкий пошук
4. **Користувач** отримує осмислений фрагмент, не уривок

## 4. Overlap — навіщо

### Проблема без overlap

Якщо чанки не перекриваються, **речення на межі** будуть розрізані:

```
Чанк 1: "...вплив бета-блокаторів на серцевий ритм. Ця терапія"
Чанк 2: "має значні протипоказання, включаючи..."
```

Запит «протипоказання бета-блокаторів» **не знайде** точно — обидва чанки мають частину відповіді, але жоден не повний.

### Розв'язання: overlap

Кінець чанка 1 повторюється на початку чанка 2:

```
Чанк 1: "...вплив бета-блокаторів на серцевий ритм. Ця терапія має значні протипоказання, включаючи..."
Чанк 2: "Ця терапія має значні протипоказання, включаючи брадикардію, гіпотензію..."
```

Тепер запит знайде **чанк 2**, де є і «протипоказання», і «бета-блокатори» (з кінця overlap).

### Чому 80 слів

Знов компроміс:
- **Більше overlap** → краще покриття меж, але **більше дублювання** (зайвий розмір індексу)
- **Менше overlap** → менше дублювання, але можна пропустити інформацію на межі
- **80 слів** = ~10-15% від 600 → невелика надмірність, гарне покриття

### Side effect

Однакова інформація може **двічі** з'явитися в топ-K (з обох чанків). Це **не проблема для оцінки**, бо в твоїй роботі qrels на рівні **doc_id**, а не chunk_id (документ релевантний, а який саме чанк — все одно). Але це треба пам'ятати на захисті.

## 5. Альтернативні стратегії

Корисно для Q&A — комісія може спитати.

### Sliding window (твій вибір)

Фіксований розмір, фіксований overlap. **Просто, робастно, передбачено**.

### Sentence-based chunking

Розрізаємо по реченнях. Чанк — це N сусідніх речень.

```python
sentences = nltk.sent_tokenize(text)
chunks = [
    " ".join(sentences[i:i+10])  # по 10 речень
    for i in range(0, len(sentences), 8)  # крок 8 = overlap 2
]
```

**Плюси:** не розрізає речення посередині.
**Мінуси:** чанки різного розміру.

### Paragraph-based

Чанк = 1 або кілька абзаців.

**Плюси:** природна одиниця, абзац — це закінчена думка.
**Мінуси:** абзаци дуже різного розміру (від 1 речення до сторінки).

### Semantic chunking

Розрізаємо там, де **семантичний розрив**. Алгоритм:
1. Обчислюємо embedding для кожного речення
2. Дивимось cosine similarity між сусідніми
3. Якщо similarity падає нижче порогу — границя чанка

**Плюси:** найбільш «правильні» кордони.
**Мінуси:** значно повільніший build; залежить від моделі.

### Recursive chunking (LangChain default)

Спробуй розрізати по `\n\n` (абзаци). Якщо чанк ще завеликий — по `\n` (рядки). Ще завеликий — по `.` (речення). Ще завеликий — по словах.

**Плюси:** адаптивно, зберігає структуру.
**Мінуси:** складніший за sliding window.

### Hierarchical chunking

Зберігаємо чанки **двох рівнів**: малі для специфічності + великі для контексту.

**Плюси:** топ-1 від малого чанка + контекст від великого.
**Мінуси:** удвічі більший індекс.

### Чому твій вибір — простий sliding window

Бо:
1. **Просто і робастно** — менше місць для помилок
2. **Однаково для всіх моделей** — чесне порівняння
3. **Зосередження дослідження** — на порівнянні моделей, не chunking-стратегій

Якби обрав semantic chunking — комісія могла б сказати «а може різниця між моделями зумовлена не моделлю, а тим, що чанки трохи інші для embedding-based стратегії». Sliding window — нейтрально по відношенню до моделі.

## 6. Як перевірити якість чанкінгу

### Метрики (не вимагаються, але корисно знати)

1. **Distribution розміру чанків** — гістограма. Має бути близька до 600 з невеликою дисперсією.
2. **Кількість речень розірваних на межі** — підраховуємо, у скількох чанках перше/останнє «речення» обрізане (без крапки на кінці чи з малої літери на початку).
3. **Recall ground-truth** — для відомих qrel'ів, чи всі релевантні чанки **знайдені**? У твоєму datasetі qrels формувалися **після** чанкінгу, тому recall=1.0 by design.

### Sanity check у твоєму репо

Подивись на `data/domains/tech/chunks.jsonl`:
```bash
wc -l data/domains/tech/chunks.jsonl   # кількість чанків
head -1 data/domains/tech/chunks.jsonl | python -c "import json,sys; print(len(json.loads(sys.stdin.read())['text'].split()))"
```

Має бути 600 ± 200 для більшості чанків.

### У застосунку

`/documents?domain=tech` — переглядаєш чанки. Якщо чанк виглядає обрізаним посередині речення — це нормально (sliding window). Якщо чанк дуже короткий або порожній — щось не так.

## 7. Як впливає на результати

### Empirical observations

Згідно з літературою:
- **Малі чанки** (100-200) → вище **Precision@k** (специфічні відповіді), але нижче **Recall@k** (релевантне розкидано)
- **Великі чанки** (1000+) → вище **Recall@k** (більший шанс зачепити релевантне), але нижче **Precision@k**
- **600-800** — типова оптимальний компроміс для більшості IR-benchmarks

### Якщо хочеш перевірити сам

```python
ingest_chunks(min_words=200, max_words=400, ...)  # малі
# rebuild index
# run benchmark
```

vs:

```python
ingest_chunks(min_words=800, max_words=1500, ...)  # великі
```

Зміни в результатах будуть видно на `/benchmark`.

### Чому це не зроблено в роботі

Бо це окремий експеримент. Робота фокусується на **порівнянні моделей** при фіксованих параметрах. Експеримент з chunking-розмірами — наступна логічна тема.

## 9. Перевірочні питання з відповідями

### Q1. Чому документи розрізають на чанки замість того, щоб індексувати цілі?

**A:** Дві причини. **Технічна:** embedding-моделі мають ліміт контексту (E5 — 512 токенів, ~380 слів). Документ на 100 сторінок не вміщається. **Семантична:** вектор цілого довгого документа стає «середнім» — втрачає специфічність. Запит «протипоказання бета-блокаторів» на 100-сторінковому документі поверне «релевантно загалом», але не вкаже сторінку. З чанками — поверне конкретний фрагмент.

### Q2. Що таке overlap між чанками і навіщо він?

**A:** Кінець одного чанка частково повторюється на початку наступного. У моїй роботі — 80 слів overlap при чанках 600 слів. Навіщо: щоб **інформація на межі** чанків не була розірвана. Якщо речення розділилось між чанками — без overlap воно недоступне жодному; з overlap — обидва чанки мають повний контекст.

### Q3. Чому всі моделі в роботі використовують **однакову** chunking-стратегію?

**A:** Для чесного порівняння. Якби BGE-M3 використовував 800-словні чанки, а E5 — 300-словні, я б не міг сказати, що різниця в nDCG викликана **самими моделями**. Однакова стратегія ізолює змінну — порівнюю саме моделі, не chunking.

### Q4. Які альтернативні стратегії існують?

**A:**
- **Sentence-based:** N сусідніх речень
- **Paragraph-based:** 1+ абзаців
- **Semantic chunking:** розрізаємо там, де різко падає cosine між сусідніми реченнями
- **Recursive (LangChain):** ієрархічно — спершу `\n\n`, потім `\n`, потім `.`, потім слова
- **Hierarchical:** малі чанки + великі контексти

У моїй роботі — sliding window (fixed-size + overlap), бо простота і робастність.

### Q5. Як параметри чанкінгу впливають на результати?

**A:** Зазвичай:
- Малі чанки (100-200) → ↑ Precision@k, ↓ Recall@k
- Великі чанки (1000+) → ↓ Precision@k, ↑ Recall@k
- 600 — оптимальний компроміс, добре працює на більшості IR-benchmarks

У моїй роботі це не вивчалося окремо — це **окремий експеримент**, перспектива.

### Q6. Що буде, якщо overlap = 0?

**A:** На межах чанків інформація може бути розірвана. Запит, що зачіпає речення на стику, **може не знайти** релевантний чанк (бо обидва містять лише частину). Recall@k знизиться. Особливо для довгих складних речень.

### Q7. Скільки чанків у твоєму корпусі?

**A:** Залежно від домена. Tech: ~770. Legal: ~1100. Medical: ~580. Загалом ~2500 чанків з 32 документів. Можна точно перевірити: `wc -l data/domains/*/chunks.jsonl`.

### Q8. Чи може один чанк бути релевантним для двох різних запитів?

**A:** Так. Один чанк (наприклад, опис симптомів) може бути релевантним і для «симптоми діабету», і для «прояви ускладнень». У `qrels.jsonl` цей чанк буде відмічений для **обох** запитів. Це нормально.

### Q9. Як впливає overlap на розмір індексу?

**A:** Збільшує. Якщо overlap = 80, а чанк = 600 — це ~13% надмірності. Загальний розмір індексу ~ збільшується на 13%. Для тисяч чанків — кілька MB extra. Прийнятно.

### Q10. Чому б не використати semantic chunking?

**A:** Бо це **складніше** і не доводить чистоту порівняння. Semantic chunking використовує embedding (якусь модель) для визначення кордонів — це додає залежність від моделі чанкінгу, яка не завжди та сама, що модель пошуку. Sliding window — простий, нейтральний, добре працює. Semantic chunking — **наступний логічний крок** у розвитку, перспектива.
