## 2. BGE-M3 — лідер у роботі

### Хто

**BAAI General Embedding M3** — третя ітерація моделей BGE від Beijing Academy of Artificial Intelligence. M3 = **M**ulti-linguality, **M**ulti-functionality, **M**ulti-granularity.

### Архітектурні особливості

- Базова архітектура: **XLM-RoBERTa large** (трансформер encoder)
- **24 шари**, 1024 hidden dim
- Multi-functional: підтримує **3 режими** одночасно:
  1. **Dense** — звичайний 1024-вимірний вектор (cosine similarity) ← це в твоїй роботі
  2. **Sparse** — як TF-IDF, але навчений на embeddings
  3. **Multi-vector** — кілька векторів на чанк для granular matching (як ColBERT)

У твоєму коді — **лише dense**. Sparse і multi-vector — більш складні у використанні, не входили в скоп.

### Тренування

Багатоетапне:
1. **MLM** (masked language modeling) — стандартне передтренування
2. **RetroMAE** — спеціальна претренувальна задача для embeddings
3. **Contrastive learning** на величезному датасеті багатомовних пар запит-документ

Підтримує **100+ мов**, у тому числі українську (тренована на uk-парах з різних джерел).

### Сильні сторони

- **Висока якість** на більшості мов
- **Довгий контекст** (8192 токенів) — підходить для майже будь-якого чанка
- **Multifunction** — можна додати sparse/multivec, якщо знадобиться (не зараз)
- **Робастність** — добре працює на різних доменах

### Слабкі сторони

- **Велика** — 568M параметрів → повільніше за E5
- **Латентність** ~220-260 мс на запит на CPU
- **Пам'ять** — модель + індекс важать кілька GB

### Чому лідер у твоїй роботі

- Tech nDCG@10: **0.6722** (1-е місце)
- Legal nDCG@10: 0.3065 (2-е, після Qwen3)
- Medical nDCG@10: **0.4339** (1-е)
- Парето-оптимальна в усіх 3 доменах

### Коди використання

`src/embedding_models.py`:
```python
class SbertEmbeddingModel:
    def __init__(self, model_name, max_seq_length=256, ...):
        from sentence_transformers import SentenceTransformer
        self.model = SentenceTransformer(model_name)
        self.model.max_seq_length = max_seq_length
        
    def encode_passages(self, texts):
        vectors = self.model.encode(texts, normalize_embeddings=True)
        return vectors
        
    def encode_queries(self, queries):
        vectors = self.model.encode(queries, normalize_embeddings=True)
        return vectors
```

Завантажується через `SentenceTransformer("BAAI/bge-m3")`.

### Як це згадати на захисті

> «BGE-M3 від BAAI — мультимовна модель з 568 мільйонами параметрів і контекстом 8192 токенів. Особливість — три режими: dense, sparse, multi-vector. У роботі я використовую dense-режим. Це найкраща модель у моїх експериментах за nDCG@10 на технічному і медичному доменах.»

## 3. E5-base — швидка альтернатива

### Хто

**E5** (EmbEddings from bidirEctional Encoder rEpresentations) від intfloat / Microsoft Research. `e5-base` — middle-розмір. Є й `e5-small`, `e5-large`.

### Архітектурні особливості

- Базова: **XLM-RoBERTa base**
- 12 шарів, 768 hidden dim
- 278 M параметрів
- Multilingual

### Особливість: префікси

E5 **вимагає** префіксів перед текстом, бо так тренувалася:

```python
# Для запитів:
queries = [f"query: {q}" for q in raw_queries]

# Для документів:
passages = [f"passage: {p}" for p in raw_passages]
```

Без префіксів — модель **працює**, але якість падає на 5-15%. Це **найпоширеніша помилка** при використанні E5.

У твоєму коді (`src/embedding_models.py:E5EmbeddingModel`):
```python
class E5EmbeddingModel:
    def encode_passages(self, texts):
        prefixed = [f"passage: {t}" for t in texts]
        vectors = self.model.encode(prefixed, normalize_embeddings=True)
        return vectors
        
    def encode_queries(self, queries):
        prefixed = [f"query: {q}" for q in queries]
        vectors = self.model.encode(prefixed, normalize_embeddings=True)
        return vectors
```

Префікси додаються **автоматично** — користувач не повинен про них пам'ятати.

### Тренування

- MLM передтренування
- Contrastive на масивному датасеті пар: пари з Reddit, Wikipedia, Stack Exchange, наукових статей, etc.
- Чітко розділені «запит» і «пасаж» з префіксами

### Сильні сторони

- **Швидка** — 70-83 мс на запит на CPU (у 3 рази швидше за BGE-M3)
- **Менша пам'ять** — 278M параметрів
- **Прийнятна якість** — друга після BGE на більшості завдань
- **Multilingual**

### Слабкі сторони

- **Короткий контекст** — 512 токенів (≈ 380 слів). Для чанків 600 слів — truncation, втрата 30-40% тексту
- Префікси треба пам'ятати при використанні

### Як це позначається у твоїх результатах

- Tech nDCG@10: 0.6121 (3-е місце, на ~0.06 нижче за BGE)
- Legal nDCG@10: 0.2567 (3-е)
- Medical nDCG@10: 0.3909 (2-е)
- Латентність ~70 мс — **3x швидше** за BGE-M3
- Парето-оптимальна (оптимальний компроміс для compromise швидкість/якість)

### Як згадати на захисті

> «E5-base — модель Microsoft з 278 мільйонами параметрів. Особливість — обов'язкові префікси query: і passage: перед текстом. Контекст 512 токенів, тому для чанків 600 слів є truncation. У моїх результатах — Парето-оптимальна швидка альтернатива BGE-M3: майже така ж якість, втричі швидше.»

## 4. nomic-embed v1.5 — найслабша

### Хто

**Nomic Embed v1.5** від Nomic AI. Open-source, з акцентом на довгий контекст і Matryoshka representations.

### Архітектурні особливості

- 137 M параметрів — **найменша** з 4-х
- 768 dim
- Контекст 8192 токенів
- BERT-based архітектура з модифікаціями

### Matryoshka Representation Learning

Особливість: модель тренована так, що **перші k вимірів** вектора несуть найважливішу інформацію. Можна **обрізати** до меншої розмірності:

```
повний вектор: [v_1, v_2, ..., v_768]  ← найкраща якість
обрізаний 256: [v_1, v_2, ..., v_256]  ← добре
обрізаний 64:  [v_1, v_2, ..., v_64]   ← компактно
```

У твоїй роботі — **не використовується**. Просто факт. Можливо для Q&A.

### Чому називається v1.5

V1 була в лютому 2024. v1.5 — оновлена з покращеним тренуванням. Є також v1.5-quantized для 1-біт компресії (не використовується в роботі).

### Сильні сторони

- **Найменша модель** — швидке завантаження, мало пам'яті
- **Довгий контекст** — 8192 токенів
- **Matryoshka** — можна стиснути indeksу
- **Open-source** — повністю на Hugging Face

### Слабкі сторони

- **Тренована переважно на англомовних даних** — на українській працює гірше за multilingual моделі
- **Найнижча якість** з 4-х моделей у твоїх результатах
- На medical (0.1668) — **гірше за BM25** (0.3222)

### Чому така низька якість у тебе

1. Слабке покриття української мови у тренувальних даних
2. Менша модель → менше «розуміння» складних доменно-специфічних текстів
3. Open-source проект без великого бюджету на multilingual

### Як це згадати на захисті

> «Nomic-embed v1.5 — найменша з 4-х моделей, 137 мільйонів параметрів. Підтримує довгий контекст 8192 токенів і техніку Matryoshka — можливість обрізати вектор без значної втрати якості. У моїх результатах це **найслабша модель** — гірше за BM25 на медичному і юридичному доменах. Причина — недостатнє представлення української мови у тренувальних даних. Це **підкреслює мою тезу**: «open-source» ≠ «найкраща», треба перевіряти на своєму домені.»

### Що зробив би для покращення

Fine-tuning nomic на українських даних. Або — взагалі замінити на іншу модель. Це **перспектива** роботи.

## 5. Qwen3-Embedding — decoder-based

### Хто

**Qwen3-Embedding-0.6B** від Alibaba (комерційна компанія, але модель open-source). Найновіша — випущена у 2025. Базується на серії Qwen3 LLM.

### Архітектурні особливості

- 596 M параметрів
- 1024 dim
- **Контекст 32 768 токенів** (32K) — найбільший серед 4-х
- **Decoder-based** — на відміну від інших 3-х

### Що означає «decoder-based embedding»

Класичні embedding моделі — **encoder-based** (BERT-style): дивляться на текст з обох сторін, bidirectional. Decoder-based — інакше: обробляють текст **зліва направо**, causal masking, як GPT.

```
Encoder:
"Я люблю котів"  → кожен токен бачить ВСІХ інших токенів
                  → bidirectional context

Decoder:
"Я люблю котів"  → кожен токен бачить ТІЛЬКИ попередні
                  → causal context
```

Для embedding береться вектор **останнього токена** (бо він «бачив» весь текст).

### Чому decoder embeddings раптом стали популярні

У 2024 побачили, що адаптовані LLM-моделі (трансформери з decoder) можуть давати **дуже якісні** embeddings. Часто **кращі** за класичні encoder-based. Це нова парадигма.

Qwen3-Embedding — одна з перших моделей цього типу від великої компанії.

### Instruction-aware

Decoder-моделі підтримують **інструкції в промптах**:

```python
text = "Instruct: Знайди документи про машинне навчання\nQuery: алгоритми класифікації"
embedding = model.encode(text)
```

Інструкція впливає на embedding — модель «знає», що шукати. У твоєму коді — **не використовуються** (без інструкцій). Можна додати — це покращить результати.

### Тренування

1. Передтренування Qwen3 LLM (текстова генерація)
2. Adaptation для embeddings:
   - Continued pretraining з contrastive loss
   - Instruction tuning з нюансованими завданнями (retrieval, similarity, classification)
3. Multilingual data

### Сильні сторони

- **Найдовший контекст** — 32K
- **Instruction-aware** — можна точно вказувати намір
- **Часто найвища якість** на MTEB (Top 5)
- **Decoder = майбутнє** embeddings

### Слабкі сторони

- **Найбільша модель** — 596M, повільніша за BGE-M3
- **Найвища латентність** — 437-463 мс на запит
- **Складніша у налаштуванні** (instruction prompts)

### Як це позначається у твоїх результатах

- Tech nDCG@10: 0.6325 (2-е)
- Legal nDCG@10: **0.3199 (1-е, лідер!)** — Qwen3 кращий за BGE на legal
- Medical nDCG@10: 0.3629 (3-е)
- Латентність найвища
- Парето-домінується BGE-M3 на tech (бо BGE швидша і якісніша одночасно)

### Чому лідер на Legal

Юридичні тексти потребують **глибокого розуміння контексту** — складні логічні зв'язки, прихована умовність, посилання. Decoder-based архітектура з більшим контекстом тут має перевагу.

### Як це згадати на захисті

> «Qwen3-Embedding від Alibaba — найновіша модель у дослідженні, випущена у 2025. Принципова відмінність: **decoder-based архітектура**, на відміну від трьох інших, які encoder-based. Базується на LLM Qwen3, адаптована для embeddings через contrastive fine-tuning. Підтримує найдовший контекст серед моделей — 32K токенів. **Лідер на юридичному домені** у моїх результатах. Decoder-based embeddings — нова парадигма 2024-2025, яка часто перевищує encoder-based на MTEB.»

## 8. Як моделі завантажуються в код

### Артефакти на диску

Кожна модель має свою папку в `artifacts/<domain>/<model_id>/`:
```
artifacts/tech/bge-m3/
├── faiss.index        ← FAISS-індекс із 1024-вимірними векторами
├── meta.jsonl         ← метадані чанків
└── model.json         ← конфігурація моделі
```

`model.json` приклад для BGE-M3:
```json
{
  "model_type": "sbert",
  "model_name": "BAAI/bge-m3",
  "params": {
    "max_seq_length": 256,
    "batch_size": 32
  }
}
```

### Динамічне завантаження

`src/embedding_models.py:load_model_from_artifacts()`:
```python
def load_model_from_artifacts(artifacts_dir, fallback_model_name):
    cfg = json.loads((artifacts_dir / "model.json").read_text())
    model_type = cfg["model_type"]
    if model_type == "e5":
        return E5EmbeddingModel(cfg["model_name"], **cfg["params"])
    elif model_type == "sbert":
        return SbertEmbeddingModel(cfg["model_name"], **cfg["params"])
    elif model_type == "nomic":
        return NomicEmbeddingModel(cfg["model_name"], **cfg["params"])
    # ...
```

### Кешування

`src/app.py:get_index_and_model()`:
```python
_cache = {}  # глобальний кеш

def get_index_and_model(model_id, domain_id):
    cache_key = f"{domain_id}/{model_id}"
    if cache_key in _cache:
        return _cache[cache_key]
    # ... завантажуємо ...
    _cache[cache_key] = (index, meta, model)
    return ...
```

Перший виклик повільний (завантаження моделі з диску), наступні — миттєві. Тому **перший пошук** у застосунку повільніший за наступні — це нормально.

## 9. Підводні камені

### ❌ Забув префікси E5

Симптом: якість на 5-15% нижче, ніж очікувано.
Розв'язання: перевір, що `encode_queries` і `encode_passages` додають `query:` / `passage:`.

### ❌ Truncation E5 на 600-словних чанках

Симптом: вектори можуть бути менш специфічні (втрачено кінець чанка).
Розв'язання: `max_seq_length=256` у твоєму коді. Альтернатива — короткі чанки (300-400 слів).

### ❌ trust_remote_code для Nomic

Nomic вимагає `trust_remote_code=True` при завантаженні:
```python
SentenceTransformer("nomic-ai/nomic-embed-text-v1.5", trust_remote_code=True)
```

Без цього — помилка.

### ❌ Qwen3 з малим batch_size на CPU

Велика модель → out-of-memory можлива при batch_size=32. Твій код використовує `batch_size=4` для Qwen3 — обережно. Повільніше, але стабільно.

### ❌ Різна модель для індексу і запиту

Якщо випадково використати BGE для індексації, а E5 для запиту → пошук не працює. У твоєму коді — захищено: `load_model_from_artifacts` бере model.json з тієї ж директорії, що і `faiss.index`.

## 10. Перевірочні питання з відповідями

### Q1. Яка з 4-х моделей не є encoder-моделлю? У чому її архітектурна особливість?

**A:** **Qwen3-Embedding-0.6B** — decoder-based, на відміну від BGE-M3, E5-base, nomic (всі encoder). Decoder використовує causal masking: токени бачать тільки попередні. Pooling робиться через **останній токен**. Базується на LLM Qwen3, адаптована для embeddings.

### Q2. Чим відрізняється використання E5 від BGE-M3 з точки зору коду?

**A:** E5 **вимагає префіксів** `query:` і `passage:` перед текстом. BGE-M3 — не вимагає. Якщо забути префікси у E5 — якість падає на 5-15%. У моєму коді префікси додаються автоматично в методах `encode_queries/passages` класу `E5EmbeddingModel`.

### Q3. Чому nomic показує найслабші результати на цьому датасеті?

**A:** Через **слабке покриття української мови** у тренувальних даних. Nomic — open-source модель з акцентом на англомовні дані. На українських корпоративних текстах її embedding-простір не оптимально розкладає семантику. **Це підкреслює мою тезу**: вибір моделі не може бути сліпим, треба перевіряти на цільових даних.

### Q4. Що таке Matryoshka representations і коли вони стали б у нагоді?

**A:** Метод тренування, при якому **перші k вимірів вектора** містять найважливішу інформацію. Можна обрізати вектор до меншої розмірності (наприклад 768 → 256) з поступовою втратою якості. **Корисно**, коли треба компромісувати з розміром індексу — на edge-пристроях, mobile, або великих корпусах. У моїй роботі — не використовується, бо корпуси малі і пам'ять не була обмеженням.

### Q5. Як BGE-M3 «multi-functional» — це означає?

**A:** Підтримує **3 режими** виходу одночасно:
- **Dense** — 1024-вимірний вектор (використано в роботі)
- **Sparse** — як TF-IDF, але нейромережевий
- **Multi-vector** — кілька векторів на чанк для granular matching
Завдяки цьому одна модель може закривати кілька стилів пошуку. У роботі — лише dense.

### Q6. Чому Qwen3 лідер саме на legal?

**A:** Юридичні тексти потребують **глибокого розуміння контексту**: складні умовні конструкції, посилання на статті, нюансна термінологія. Decoder-based архітектура Qwen3 з найдовшим контекстом (32K токенів) у цьому має перевагу. Encoder-based моделі трохи гірше справляються з такою складністю.

### Q7. Чому BGE-M3 краще за Qwen3 на tech і medical, але гірше на legal?

**A:** Гіпотеза: у tech і medical більше «фактичних» питань (запитав термін → знайшов опис). BGE-M3 з його сильним мультимовним тренуванням і компактнішою архітектурою тут ефективніше. У legal — складніша логіка, де decoder shines. Не маю емпіричного доведення, але це узгоджена з MTEB-бенчмарками інтуіція.

### Q8. Чому E5 — Парето-оптимальна, а Qwen3 — ні (на tech)?

**A:** Qwen3 повільніша за BGE-M3 (463 vs 222 мс) **і** менш якісна (0.6325 vs 0.6722). Тобто BGE-M3 **домінує** Qwen3 на tech: краще за обома основними критеріями. E5-base — не домінується ніким, бо хоч якість трохи нижча за BGE, латентність значно краща (70 vs 222 мс). Це і є оптимальний компроміс.

### Q9. Як ти би додав 5-ту модель — наприклад, OpenAI text-embedding-3-large?

**A:**
1. Створив би клас `OpenAIEmbeddingModel` в `src/embedding_models.py` з методами `encode_queries/passages`, що викликають OpenAI API.
2. Додав би тип `"openai"` у `load_model_from_artifacts`.
3. Створив би `model.json` з `model_type=openai`, `model_name=text-embedding-3-large`.
4. Викликав би `build_index.py` для побудови індексу.
5. Запустив би `evaluate_benchmark.py`.

Технічно — кілька десятків рядків. Не зробив тільки тому, що (а) немає API ключа, (б) фокус роботи — open-source альтернативи.

### Q10. Якщо я хочу швидку модель з прийнятною якістю — що порадиш?

**A:** **E5-base** з max_seq_length=256:
- Латентність ~70 мс на CPU
- Якість на ~10% нижче за BGE-M3 на tech
- Multilingual, підтримує українську
- Парето-оптимальна у моїх експериментах
- Менша модель — менше пам'яті

Якщо ще швидше треба — **BM25** з ~1 мс. Втрата якості значно більша (на ~50%), але іноді прийнятно.
