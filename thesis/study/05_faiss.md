# 05. FAISS — швидкий пошук по векторах

> **TL;DR:** FAISS (Facebook AI Similarity Search) — бібліотека для пошуку найближчих векторів. Має 20+ типів індексів: від точних (IndexFlatIP) до наближених (HNSW, IVF, PQ). У твоїй роботі — IndexFlatIP: точний пошук, ідеально для оцінювання якості моделей без апроксимації. Для production з мільйонами векторів — HNSW або IVF.

## 1. Що таке similarity search

### Постановка задачі

Дано:
- **База** з N векторів розмірності d (наприклад N=1,000,000, d=768)
- **Query вектор** q розмірності d
- **K** — кількість найближчих, що треба знайти

Знайти: K векторів з бази, найближчих до q (за метрикою — cosine, L2, IP).

### Найпростіше рішення (brute force)

```python
distances = [cosine_distance(q, v) for v in database]
indices = argsort(distances)[:K]
```

Складність: **O(N × d)** на запит. Для 1M × 768 = ~768 мільйонів операцій. На CPU — секунди. На production — неприйнятно.

### Що робить FAISS

Реалізує **спеціалізовані структури даних і алгоритми**, щоб робити це **набагато швидше**, ціною трохи точності (для ANN). Або **так само точно**, але оптимізовано (для exact).

---

## 2. Чому це складна задача

### Curse of dimensionality

У низькій розмірності (2D, 3D) є kd-tree, R-tree — швидкі за O(log N). У високій (768+):
- Більшість векторів виявляються **майже однаково далекими** один від одного
- Класичні структури деградують до O(N)
- Тому потрібні спеціалізовані техніки для embeddings

### Memory bottleneck

1 мільйон векторів × 768 dim × 4 байти (float32) = **3 GB**. Зберігати все в RAM — дорого. Тому FAISS має методи **компресії** (PQ).

### CPU vs GPU

FAISS оптимізована і для CPU, і для GPU. У твоїй роботі CPU-only — Flat достатньо.

---

## 3. Точний vs наближений

### Exact (точний) пошук

Гарантовано повертає **справжні топ-K**. Перевіряє всі вектори.

- Плюси: 100% recall
- Мінуси: O(N) на запит → повільно для великих N

Приклад: IndexFlatIP, IndexFlatL2.

### ANN (Approximate Nearest Neighbor)

Повертає **приблизно** топ-K. Може пропустити деякі, додати неоптимальні.

- Плюси: O(log N) або краще на запит → дуже швидко
- Мінуси: < 100% recall (зазвичай 95-99%, можна тюнити)

Приклади: HNSW, IVF, LSH.

### Trade-off

| Параметр | Exact (Flat) | ANN (HNSW/IVF) |
|---|---|---|
| Recall | 100% | 95-99% |
| Швидкість пошуку | повільніше | швидше (10-1000x) |
| Memory | той же | трохи більше (індекс структура) |
| Index build time | дуже швидко | повільніше |

## 4. IndexFlatIP — точний пошук

### Як це працює

«Flat» означає **прямий, без хитрої структури**. Усі вектори зберігаються підряд у масиві. Пошук — лінійний прохід.

```
[v1] [v2] [v3] ... [vN]
```

Для запиту q:
```
for i in 1..N:
    scores[i] = dot_product(q, v_i)
return top_K(scores)
```

### IP = Inner Product

IP — inner product. Для нормалізованих векторів = cosine similarity (див. файл 03).

### Чому SO повільно — і чому це OK для тебе

Для N=1,000,000 і d=768: 768M множень + 768M додавань на запит. На CPU ~50-200 мс.

Для N=1000 (твої корпуси — тисячі чанків): 1000 × 768 = 768K множень. **Мілісекунди**. Швидко.

Якби в тебе було 100M чанків — Flat був би неприйнятним. Потрібен HNSW. Але для дослідницького benchmark з кількома тисячами чанків — Flat ідеальний.

### Переваги Flat для твого випадку

1. **100% recall** — точно знаходить топ-K. Це гарантує **чесне** порівняння моделей.
2. **Жодних параметрів** для тюнингу — нема варіативності.
3. **Швидко на малих корпусах** — мс.
4. **Простий код** — менше можливостей помилитися.

## 5. HNSW

### Що це

**Hierarchical Navigable Small World graph** (Malkov, Yashunin, 2016). Сучасний топ-вибір для ANN.

### Ідея

Будує **багатошаровий граф**:
- Верхній шар — кілька «найважливіших» вузлів (як континенти)
- Середні шари — більше вузлів (країни, міста)
- Нижній шар — усі вектори

Пошук:
1. Стартуємо з верхнього шару — швидко знаходимо приблизну область
2. Спускаємось униз — деталізуємо пошук
3. На нижньому шарі — точно знаходимо найближчих сусідів

**Аналогія:** як GPS. Спочатку дивимось на континент, потім місто, потім вулицю.

### Параметри

- `M` — скільки сусідів зберігати на вузол (16-64, типово 16). Більше M → точніше, дорожче.
- `efConstruction` — параметр при побудові графа (200 типово)
- `efSearch` — параметр при пошуку (10-200). Більше → точніше, повільніше

### Швидкість

При параметрах за замовчуванням, для N=1M:
- Flat: ~100 мс
- HNSW: ~1-5 мс (100x швидше)
- Recall: 95-99%

### Коли використовувати

- Корпуси 100K+
- Можна жертвувати recall на 1-5%
- Потрібна низька latency

## 6. IVF — Inverted File Index

### Ідея

Кластеризація + інверт-індекс.

1. **Тренувальна фаза:** кластеризуємо всі вектори бази (наприклад k-means з n_clusters=1024). Кожен вектор приписується до 1 кластера.
2. **Зберігаємо** для кожного кластера — центроїд і список векторів.
3. **Пошук:**
   - Знаходимо `nprobe` найближчих центроїдів до запиту
   - Шукаємо тільки серед векторів цих кластерів (а не всіх N)

### Швидкість

Якщо корпус 1M векторів і 1024 кластери, в середньому 1000 векторів на кластер. При `nprobe=10`, перевіряємо 10000 векторів замість 1М — **100x швидше**.

### Параметри

- `nlist` — кількість кластерів при побудові (типово √N)
- `nprobe` — скільки кластерів дивитись при пошуку (10-100)

### IVF + PQ

Часто комбінують з product quantization для компресії пам'яті — `IndexIVFPQ`.

---

## 7. PQ — Product Quantization

### Проблема

Якщо у тебе 1B (мільярд) векторів × 768 dim × 4 байти = **3 TB**. Не вмістити в RAM.

### Рішення PQ

Стискаємо кожен вектор у **набагато коротший код**.

Як: розбиваємо вектор на M піделементів, кожен квантизуємо окремо в 256 кодів. Наприклад, 768 dim → 16 піделементів по 48 dim. Кожен піделемент → 1 байт (0-255). Замість 3072 байтів → 16 байтів. **200x компресія**.

Звичайно, точність падає. Але часто прийнятна.

### Коли потрібно

- Дуже великі корпуси (10M+ векторів)
- Обмежена пам'ять

### У твоїй роботі

Не використовується. Корпуси малі.

## 8. Як обрати індекс під твою задачу

| Розмір корпусу | RAM available | Recall requirement | Рекомендований індекс |
|---|---|---|---|
| < 10K | Так | 100% | IndexFlatIP |
| 10K-100K | Так | 100% | IndexFlatIP |
| 100K-1M | Так | 95-99% | IndexHNSWFlat |
| 100K-1M | Обмежено | 95-99% | IndexIVFFlat |
| 1M-100M | Так | 90-95% | IndexHNSWFlat |
| 1M-100M | Обмежено | 90-95% | IndexIVFFlat або IVFPQ |
| 100M+ | Обмежено | 80-95% | IndexIVFPQ |

### У твоєму випадку

Tech корпус: ~770 чанків (10 документів × ~77 чанків each).
Legal: ~1100 чанків.
Medical: ~580 чанків.

Усе — << 10K. **IndexFlatIP — оптимальний**.

---

## 9. Чому в твоїй роботі — Flat

### Аргумент 1: Малий розмір корпусу

Тисячі чанків. Flat дає мс-латентність. Немає потреби в ANN.

### Аргумент 2: Точність важливіша за швидкість

Робота **оцінює якість моделей**, не швидкість індексу. Якби обрав HNSW з recall 97% — частина результатів була б «несправжніми топ-10». Це **запровадило б шум** у оцінку моделей. Не знав би, чи різниця в nDCG зумовлена самою моделлю, чи варіацією ANN.

### Аргумент 3: Reproducibility

Flat детермінований. HNSW — теж, але через параметри. Простіше відтворити експеримент.

### Аргумент 4: Простота

Менше параметрів — менше можливостей помилитися. Менше пояснень комісії.

### Що сказати на захисті

> «Я обрав IndexFlatIP, бо корпуси в роботі малі — тисячі чанків. Flat дає точний пошук без апроксимацій, що гарантує **чесне** порівняння саме моделей, а не алгоритмів пошуку. Якби корпус був 1M+ — обрав би HNSW або IVF з тюнингом параметрів. Це згадано у перспективах роботи.»

## 10. Використання FAISS у коді

### Базовий приклад

```python
import faiss
import numpy as np

# 1. Створюємо індекс
dim = 768
index = faiss.IndexFlatIP(dim)

# 2. Готуємо вектори (нормалізовані)
N = 1000
vectors = np.random.rand(N, dim).astype('float32')
faiss.normalize_L2(vectors)

# 3. Додаємо до індексу
index.add(vectors)
print(f"Index has {index.ntotal} vectors")

# 4. Пошук
query = np.random.rand(1, dim).astype('float32')
faiss.normalize_L2(query)
scores, indices = index.search(query, k=10)

# scores.shape = (1, 10), indices.shape = (1, 10)
print("Top-10 scores:", scores[0])
print("Top-10 indices:", indices[0])
```

### Збереження на диск

```python
faiss.write_index(index, "my.index")

# Завантаження
loaded = faiss.read_index("my.index")
```

### У твоєму репо

`src/build_index.py`:
```python
index = faiss.IndexFlatIP(dim)
index.add(vectors)
faiss.write_index(index, str(artifacts_dir / "faiss.index"))
```

`src/app.py:get_index_and_model()`:
```python
index = faiss.read_index(str(artifacts_dir / "faiss.index"))
```

`src/app.py:do_search()`:
```python
query_vector = model.encode_queries([query]).astype("float32")
scores, indices = index.search(query_vector, top_k)
# scores[0] = масив cosine similarities топ-K
# indices[0] = позиції в meta.jsonl
```

### Артефакти на диску

В директорії `artifacts/<domain>/<model_id>/`:
- `faiss.index` — серіалізований FAISS-індекс
- `meta.jsonl` — метадані (doc_id, chunk_id, text) для кожної позиції
- `model.json` — конфігурація моделі (model_name, type, тощо)

Indices з FAISS — це позиції в meta.jsonl (рядок номер). Тобто `indices[0][0]` = індекс топ-1 → беремо рядок `indices[0][0]` з meta.jsonl → отримуємо chunk_id і text.

## 11. Перевірочні питання з відповідями

### Q1. Що означає «Flat» і «IP» в назві IndexFlatIP?

**A:** **Flat** — без хитрої структури індексу: вектори зберігаються підряд, пошук — лінійний прохід. **IP** — Inner Product (скалярний добуток). Для нормалізованих векторів IP = cosine similarity. Тому IndexFlatIP — це точний пошук за косинусною схожістю.

### Q2. Точний vs наближений пошук — у чому компроміс? Чому в роботі обрано точний?

**A:** Точний (Flat) дає 100% recall, але повільніший — O(N) на запит. ANN (HNSW, IVF) — швидші, але recall зазвичай 95-99%. У моєму випадку корпуси малі (тисячі чанків), Flat дає мс-латентність — швидкість не проблема. А точність критична: я **порівнюю моделі**, треба, щоб різниця у nDCG була через моделі, а не через апроксимацію індексу. Тому Flat.

### Q3. Як після `index.search(...)` ти отримуєш текст знайденого чанка?

**A:** `index.search()` повертає `(scores, indices)`. `indices[0][i]` — позиція в індексі (рядок номер). Цей рядок відповідає рядку в `meta.jsonl`, який містить `chunk_id`, `text`, `source`. Тобто: `meta = load_meta(meta_path); chunk = meta[indices[0][i]]`.

### Q4. Якщо в тебе 10M векторів — який індекс рекомендуєш?

**A:** **IndexHNSWFlat** з параметрами M=32, efSearch=64 — типовий компроміс recall/швидкість. Recall ~98%, швидкість ~5-10 мс. Якщо RAM обмежено — IndexIVFFlat з nlist=1024, nprobe=10. Якщо ще менше RAM — IVFPQ.

### Q5. Що таке `nprobe` в IVF?

**A:** Кількість найближчих кластерів, у яких шукати. **Більше nprobe** → перевіряємо більше векторів → вище recall, повільніше пошук. Типово 10-100. Це **runtime параметр** — можна змінювати без перебудови індексу.

### Q6. Що буде, якщо не нормалізувати вектори перед IndexFlatIP?

**A:** Пошук поверне топ-K по dot product, а не cosine. Документи з **довшими** векторами (більше слів, більша норма) отримають вищі scores не через семантичну схожість, а через довжину. Результат — упереджений у бік довгих документів. У моєму коді нормалізація робиться обов'язково (в методах `encode_passages/queries`).

### Q7. Чи можна додавати вектори до FAISS-індексу інкрементально?

**A:** Так — `index.add(new_vectors)`. Усі індекси FAISS це підтримують. Деякі (IVF) потребують **попереднього тренування** (cluster centroids) перед `add`. Flat не потребує — додавай скільки хочеш.

### Q8. Чи зберігає FAISS оригінальні вектори, чи лише індексну структуру?

**A:** Залежить від індексу. **Flat** — зберігає **усі вектори в повному розмірі** (тому й «3 GB для 1M × 768»). **PQ варіанти** — зберігають стиснені коди, не оригінальні вектори (тому повертають **апроксимовані** distances). Для Flat можна `index.reconstruct(i)` — отримати оригінальний i-й вектор.

### Q9. Чому FAISS — від Facebook AI, але активно використовується відкритими проєктами?

**A:** Бо це **open-source бібліотека** (MIT license), яку Facebook опублікував у 2017. Активно розвивається, найкраще співвідношення швидкість/якість серед безкоштовних. Альтернативи: Annoy (Spotify), HNSWlib, ScaNN (Google).

### Q10. Що означає, коли при пошуку повертається `-1` як index?

**A:** «Не знайдено» — це коли у нас < K векторів в індексі, і деякі позиції у відповіді не заповнені. Наприклад, якщо в індексі 5 векторів, а ти просиш топ-10 — отримаєш 5 реальних + 5 позицій з -1. У твоєму коді є фільтр `if 0 <= idx < len(meta)` саме для цього.
